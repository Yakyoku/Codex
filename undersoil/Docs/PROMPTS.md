======================================================================
# 第3部 あとで使う指示集（今は実行しない。Docs/PROMPTS.md に保存する）
======================================================================
私が短い言葉で伝えたら、該当する指示を実行する。
番号・場所・対象・機器など足りない情報は、私の言葉から読み取る。読み取れなければ1回だけ質問する。
どの指示でも、直したものは Netlify に公開し、URL を装飾なしの単独行で示す。
画面版を直したら、VR 版にも同じ直しが必要かを確かめる。
作業の前に Docs/GAME_BRIEF.md と Docs/HANDOFF.md を読み、scripts/setup.sh で環境を整える。

## ステージ追加（例：「ステージ2の根のまわりを作って」）
1. 調査
   その場所の実際の構造と、そこに実在する生き物の種類、大きさ、色、質感、動き、働きを調べ、
   Docs/REFERENCE/（場所の名前）.md にまとめる。
   新しく登場させる種を生き物台帳に追加し、形の仕様書を作り、サブエージェントに事実確認させる。
2. 設計（GDD に追記してから作る）
   - 痩せた状態と豊かな状態の、見た目の差（3点以上）
   - その場所の生き物の働きに由来する固有の遊び（1つ）。画面版と VR 版それぞれでの遊ばせ方
   - 道のり：入口 → 3つの区域 → 山場。区域ごとの見せ場
   - 地上の変化の演出（実在するどの植物が、どう育ち、どう咲くか）
   - 新しく出会う生き物（3〜6種。和名・学名・初登場の説明文）
   - このステージの容量と描画負荷の見積もり（予算表の範囲に収まること）
3. 制作
   ステージ1で確立した基準を下回らないこと。
   共通基盤を再利用し、そのステージに固有の部分だけを新しく作る。ステージは後から読み込む形にする。
   画面版を先に仕上げ、続けて VR 版を仕上げる。
4. 検証
   自動操作での通しプレイ、エラーゼロ、予算表の範囲内。
   新しい生き物すべてに、確認用の画像、紹介カード、図鑑の項目があること。
5. 報告
   公開 URL、スクリーンショット、動画、容量、自己評価、進捗確認ページの更新、私に頼む実機確認の内容。

## 実機の結果を伝えるとき（例：診断結果の貼り付け、スクリーンショットの添付、「iPadだとこう見える」）
- 貼られた診断結果を読み取り、機器ごとの表に整理して Docs/DEVICE_RESULTS.md に追記する。
- 予算表の目標と比べ、届いていない項目と、その原因の候補を挙げる。
- 添付されたスクリーンショットを見て、狙いとの違いを書き出す。
- 対処を行い、公開し、もう一度確かめてほしい点を具体的に伝える。

## VR で酔う・カクつくとき（例：「VRで酔う」「VRがカクカクする」）
- 私から、どの場面で、どんな動きのときに起きたかを聞き取る。足りなければ1回だけ質問する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影の数を数え、VR の上限と比べる。
- 描画の負荷を下げる（半透明を減らす、光と影を軽くする、LOD を早める、粒子を減らす、描画解像度を調整する）。
- 酔いやすい動き（回転、急な加速、勝手なカメラの動き、高速の移動）を洗い出し、
  速度の調整、視野を絞る機能の強化、移動方法の変更で対処する。
- 対処後の版を公開し、私に Quest 3 での再確認を頼む。見てほしい点を具体的に書く。

## VR で動かない・表示がおかしいとき（例：「VRに入れない」「VRで画面が乱れる」）
- 私から、表示されたメッセージ、起きた手順、画面の様子を聞き取る。
- WebXR のエミュレーターで同じ手順を再現できるか試す。
- 原因の候補を挙げ、可能性の高い順に対処を試す。試したことと結果を表で報告する。

## iPad や iPhone で動かない・落ちる・表示がおかしいとき（例：「iPadで落ちる」）
- 私から、機種、OS の版、起きた場面、表示されたメッセージ、診断ページの結果を聞き取る。
- WebGPU で起きている場合は、設定で WebGL 2 に切り替えて同じ症状が出るかを私に確かめてもらい、原因を切り分ける。
- 読み込む素材の量、テクスチャの大きさ、描画解像度、後処理を見直し、メモリの使用を減らす。
- 対策後の版を公開し、私に実機での再確認を頼む。

## 読み込みが遅い・容量が大きいとき（例：「読み込みが遅い」）
- 読み込むファイルの容量の内訳を計測する。
- 大きい順に原因を5つ挙げる（テクスチャ、メッシュ、音、フォント、プログラムなど）。
- 見た目を落とさない対策から順に適用する（圧縮形式の見直し、解像度の調整、後読み込みへの移動、不要なコードの除去）。
- Netlify の配信設定（圧縮とキャッシュ）が正しく効いているかを確かめる。
- 対策ごとに、前後の容量を表で報告する。

## 生き物が本物と違うとき（例：「トビムシが本物と違う」。写真の添付があればそれを使う）
1. 私が添付した写真があれば、それを最優先の資料にする。
   なければ、その種の姿についての記述を新たに調べ直し、形の仕様書を見直す。
2. 現在のモデルの確認用の画像と見比べ、
   違いを「体のつくり・比率・色・透け具合・表面の質感・動き方」の6項目で書き出す。
3. 違いが大きい順に、モデルを作るスクリプトを直す。直すたびに確認用の画像を作り直す。
4. 台帳の記述に誤りが見つかったら、台帳、紹介カード、図鑑もあわせて直す。
5. 直す前と直した後の比較画像を、進捗確認ページに載せる。

## 紹介や図鑑を直したいとき（例：「説明が長い」「説明が難しい」「紹介が邪魔」）
- 説明文を、1〜2文で、専門用語に言い換えを添えた形に書き直す。事実は台帳から外れないこと。
- 表示の長さ、出すタイミング、見せ方、文字の大きさを、画面版と VR 版それぞれで見直す。
- 全種の紹介文を一覧にして、直す前と直した後を表で報告する。

## 映像がゲームっぽいとき（例：「映像がゲームっぽい」。スクリーンショットの添付があればそれを使う）
1. 現在の画面を、決まった場面で撮る。私が添付した画面や参考写真があれば、それと並べる。
2. 違いを「形・色・質感・光・動き・空気感」の6項目で書き出す。
3. 差が大きい順に3項目を直す。直すたびに同じ場面を撮り直して比べる。
4. 直す前と直した後の比較画像と、容量と描画負荷への影響を報告に添える。

## 大画面で粗が見えるとき（例：「テレビで見るとギザギザする」「カクつく」）
- 私から、どの場面で何が気になるかと、診断ページの結果を聞き取る。
- 輪郭のギザギザ、濡れた面のちらつき、ぼやけたテクスチャ、文字の小ささへの対策を行う。
- 引っかかりの原因（読み込み、シェーダーの準備、粒子、影）を調べて対処する。
- 内部の描画解像度、アンチエイリアスの設定を見直す。
- 公開し、同じ場面をもう一度確かめてもらう。

## 操作が気持ちよくないとき（例：「泳ぐ操作が気持ちよくない」）
- 対象（歩く／泳ぐ／菌糸の滑走／道具など）と入力方法（キーボード＋マウス／ゲームパッド／タッチ／Quest 3 のコントローラー）
  について、入力から動き出しまでの遅れ、加速と減速の曲線、慣性、カメラの追従と揺れ、
  手応え（一瞬の間・振動・音・光）を見直す。
- 調整値はデータファイルに出し、変更前と変更後の値を表で報告する。
- 設定画面に、その場で調整できる一時的なつまみを用意し、私が実機で好みの値を探せるようにする。

## 芽吹きや開花をもっと感動的にしたいとき（例：「開花の演出を作り直して」）
- 土の活力が上がるにつれて、水が染みる、菌糸が伸びる、生き物が集まる、根が伸びる、の順番を1秒単位で設計する。
- 画面版では、カメラが土の中から地上へ抜け、芽・葉・つぼみ・花の順に、早回しで見せる。
  VR 版では、プレイヤーを地表に立たせたまま、周りで植物が育っていく様子を見せる。
  光は朝の斜めの光を基本にする。成長の順序と形は、その種の実際の育ち方に合わせる。
- 音は地下の静けさから始め、地上に出た瞬間に音楽と自然音が開く。花が開く瞬間に和音の頂点を合わせる。
- 演出の絵コンテ（文章でよい）を先に書いてから実装する。

## 音が薄いとき（例：「音が薄い」）
- いま鳴っている音を一覧にし、無音になっている動作や場面を洗い出す。
- 足りない音を追加する：移動、接触、道具、仲間と相手、環境、地上の自然音、紹介と図鑑、UI。
- 音量のバランス、水の中のこもり具合、距離による減衰、VR での音の方向感を調整する。
- 追加した音による容量の増加を報告する。

## 動きが重いとき（例：「動きが重い」。診断結果の貼り付けがあればそれを使う）
目標は、PC 高画質とモバイル高画質で60fps、互換で30fps以上、VR で72fps以上。
- 診断結果から、どの機器のどの場面が目標を下回っているかを特定する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影、後処理、粒子の数を数え、重い原因の候補を挙げる。
- 見た目を落とさない対策から順に適用する。
- 公開し、同じ場面の診断をもう一度お願いする。

## ライブラリを新しい版に上げたいとき（例：「Three.jsを最新にして」）
- 最新の正式版と、その変更点のうちこのゲームに効くもの（描画、性能、WebGPU、VR、不具合の修正）を調べて報告する。
- 作業用の枝で版を上げ、自動テストとスクリーンショットの比較を行い、下書き用の URL に公開する。
- 問題がなければ切り替え、問題があれば原因と選択肢を報告する。Docs/TECH.md の版の記録を更新する。

## 全体の完成度を上げたいとき（例：「厳しい目で採点して」）
制作に関わっていない厳しいレビュアーの立場のサブエージェントに、スクリーンショットと動画と公開 URL の情報を渡して採点させる。
- 最初の5分で感じる「安っぽさ」と「待たされ感」を10個挙げる。
- 市販のAA級タイトルや、評価の高い Web の 3D 作品・VR 作品と比べて足りない点を、
  映像・生き物の正確さ・操作・音・演出・UI・読み込みの軽さ・VR の快適さに分けて挙げる。
- 効果が大きく手間が小さい順に並べ、上位5個を直す。
- 直す前と直した後の比較を、進捗確認ページに載せる。
