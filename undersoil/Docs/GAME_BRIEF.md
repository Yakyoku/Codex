# 役割
あなたは、AA級タイトル、Web 向け 3D コンテンツ、VR コンテンツの開発経験を持つ、
ゲームディレクター兼テクニカルアーティスト兼リードエンジニアです。
Claude Code のクラウド環境の中だけで、下記のゲームを、ブラウザで動く Web アプリとして企画から実装・検証・公開まで
一貫して制作してください。公開先は Netlify です。PC へのインストールは一切前提にしません。
遊び方は2通り用意します。画面で遊ぶ「画面版」（PC・iPad・iPhone）と、Meta Quest 3 で立体的に遊ぶ「VR版」です。
私は主にスマホや iPad から進捗を確認し、完成品は PC のブラウザを50インチのテレビに映す形と、Meta Quest 3 の両方で遊びます。

# 作業環境（Claude Code のクラウド環境）
この環境の性質を踏まえて動くこと。

- 画面のない Linux の作業環境である。GPU はなく、CPU とメモリも少ない。
  Unity や、画面を開いて使う Blender は動かせない。すべてをコードとコマンドで作る。
- セッションは使い捨てである。環境が作り直されると、コミットしていないものは消える。
  - 作業の区切りごとにコミットしてプッシュする。生成した素材も、それを作るスクリプトも、リポジトリに入れる。
  - 必要な道具をまとめて入れ直すスクリプト scripts/setup.sh を作り、新しいセッションの最初に実行する。
  - セッションの終わりと、大きな区切りごとに、Docs/HANDOFF.md を更新する。
- ネットワークには制限がある。npm、PyPI、GitHub には届くが、それ以外のサイトには届かないことが多い。
  - 届く先と届かない先を第1部で調べる。
  - 届かないサイトの素材（写真、テクスチャ、音、フォント）に頼らない設計にする。素材は自分で生成する。
  - どうしても必要なサイトがある場合は、そのドメイン名と理由を私に伝える。私が環境の設定で許可できるか検討する。
- ローカルの Web サーバーは立てない。
  画面の確認は、ブラウザの自動操作で、ビルド結果のファイルを仮の https の住所から読み込ませる方法
  （Playwright の経路の差し替え）で行う。
- 長く走り続けるコマンドは途中で止められることがある。重い処理は小分けにし、途中結果を保存しながら進める。
- 調査、事実確認、第三者目線のレビューは、サブエージェントに分ける。

# 採用する道具
次の組み合わせは、同種のクラウド環境で実際に動くことを確かめてある。これを使う。
第1部で、この環境でも同じように動くかを確かめ直し、版の違いは Docs/TECH.md に記録する。

- 3D の描画：Three.js（確認した版は r187）。three/webgpu の WebGPURenderer を使う。
  1つの描画エンジンで、WebGPU と WebGL 2 の両方に対応でき、WebGPU が使えない環境では自動で WebGL 2 に切り替わる。
  マテリアルと後処理は TSL（Three.js のノード式シェーダー）で書く。同じ記述が両方の方式で動くので、見た目をそろえられる。
  VR（WebXR）にも標準で対応している。
- ビルド：Node.js、TypeScript、Vite（または esbuild）。
- モデル・リグ・アニメーション・焼き込み：Blender を Python のモジュールとして使う（pip で入る bpy。確認した版は 5.3）。
  画面なしで、モデリング、ジオメトリノード、リグ、アニメーション、Cycles での描画と焼き込み（CPU）、
  GLB 形式（Draco 圧縮）での書き出しができることを確かめてある。
  キャラクターと生き物は、すべてこの方法で、Python のスクリプトとして作る。
- 素材の最適化：glTF Transform（メッシュの圧縮、テクスチャの縮小と変換、重複の除去）。
- 画像の加工：ImageMagick、Python の画像ライブラリ。
- 音：ffmpeg（変換と圧縮）、Python による音の合成。実行時はブラウザの Web Audio API を直接使う。
- 画面の確認：Playwright と、環境に入っている Chrome。画面なしで動かし、スクリーンショットを撮って自分で見る。
- 版の管理：Git と GitHub。
- 公開：Netlify（接続済みの Netlify の連携機能、または Netlify CLI）。

確かめてある制約（設計に織り込むこと）：
- この環境の Chrome では、WebGL 2 の画面はスクリーンショットに正しく写る。
  WebGPU は初期化も描画もエラーなく動くが、スクリーンショットには真っ黒にしか写らない。
  そのため、見た目の確認は WebGL 2 で行い、WebGPU は「エラーなく動くこと」までを確かめる。
  WebGPU での実際の見た目と速さは、私が実機で確かめる（下の「検証と報告」に従う）。
- GPU がないので、この環境で測った fps には意味がない。速さは実機で測る。
- 外部の写真サイトや素材サイトには届かない。参考写真を自分で見られない可能性が高い。
  （対処は「実在の生き物だけを使う」と「映像の基準」に従う）

追加の候補（必要になった時点で、動くことを確かめてから採用する）：
- 物理演算：Rapier（WebAssembly 版）
- VR の模擬：Meta の WebXR エミュレーター（iwer）。ヘッドセットなしで VR の動作を自動確認するために使う。
- テクスチャの KTX2 圧縮：この環境で使える変換手段があれば採用する。なければ WebP を使う。

Web アプリは「ビルドして、公開して、実際の機器のブラウザで開く」までが通って初めて動いたと言える。
中身を作る前に、画面版と VR 版の両方の経路を、空に近い状態で最後まで通す。

1. 環境を調べる。
   - OS、CPU の数、メモリ、空きディスク、GPU の有無。
   - 入っている道具とその版（node、npm、python、pip、git、gh、ffmpeg、Chrome、ImageMagick など）。
   - ネットワークの届く先（npm、PyPI、GitHub、Netlify の API）と、届かない先の例。
   - 使えるツール・スキル・連携機能（特に Netlify と GitHub）。
2. 道具を入れ、scripts/setup.sh にまとめる。
   - Blender の Python モジュール（bpy）、Three.js、ビルドの道具、Playwright、glTF Transform など。
   - Three.js は最新の正式版を調べて使う。
3. 素材の経路を通す。
   - bpy のスクリプトで、でこぼこのある土の粒を1つ作り、茶色のマテリアルを付け、AO を焼き込み、GLB で書き出す。
   - glTF Transform で最適化する。
4. 画面版の最小のページを作る。
   - WebGPURenderer で、WebGPU を第一、WebGL 2 を予備にして、3. の GLB を表示する。

5. VR 版の最小のページを作る。
   - 同じ GLB を、VR に入って見回せる形で表示する。VR 中は WebGL 2 で動かす。
   - 「VR で遊ぶ」のボタンを置く。
6. この環境で画面を確かめる。
   - Playwright と Chrome で、ビルド結果を仮の https の住所から読み込ませ、スクリーンショットを撮って自分で見る。
   - WebGL 2 で絵が正しく出ていること、WebGPU でエラーなく初期化と描画ができることを確かめる。

## ゲームの概要
- 仮題：UNDERSOIL（正式タイトルは日本語と英語で3案ずつ提案する）
- ジャンル：3Dアクションアドベンチャー。画面版は三人称視点（一人称に切替可能）、VR 版は一人称視点。
- 対象：大人。リアルで美しく、自然ドキュメンタリーと映画の中間のトーン。
  戦いよりも、命が育っていく喜びが主役の、前向きなゲーム。
- プラットフォーム：ブラウザで動く Web アプリ。インストール不要で、URL を開けば遊べる。
  - 画面版：Windows PC の Chrome または Edge（RTX 4060 クラス。50インチのテレビに全画面表示）、
    最新の iPad・iPhone の Safari
  - VR 版：Meta Quest 3 の標準ブラウザ
  - タイトル画面で「画面で遊ぶ／VR で遊ぶ」を選べるようにし、行き来できるようにする。
    Quest 3 のブラウザで開いたときは、VR 版への案内を目立たせる。
- 操作：キーボード＋マウス、ゲームパッド、タッチ、Quest 3 のコントローラー
- 言語：日本語（UI・字幕・ナレーション）。文言は外部ファイルに分ける
- 分量：1ステージ15〜25分、全体で3〜4時間
- 画面版と VR 版は、物語・ステージ・生き物・図鑑を共通にする。違うのは、見せ方と操作と描画の密度だけである。

## Web アプリとしての前提（最重要）
ブラウザで動かすことによる制約を、設計の最初から織り込む。後から削るのではなく、最初から予算の中で最高の絵を作る。

- 描画の仕組み：
  - 画面版は WebGPU を第一とし、WebGPU が使えないブラウザでは WebGL 2 に自動で切り替わるようにする。
  - VR 版は WebGL 2 で動かす（Quest 3 のブラウザでは、VR 中の WebGPU はまだ試験的な機能のため）。
  - 実行時に、端末の種類と動作中の描画方式を判定し、次の品質段階を自動で選ぶ。設定画面で手動でも選べるようにする。
    1. PC 高画質（WebGPU）：PC の Chrome・Edge 向け。画面版の完成品の基準。
       WebGPU でのみ使える機能（GPU 上の計算による大量の粒子など）を上乗せする。
    2. モバイル高画質（WebGPU）：最新の iPad・iPhone の Safari 向け。
       最新の機種は WebGPU が使え、処理性能も高い。PC 高画質と同じ機能を使い、解像度と密度を機種に合わせて調整する。
       高性能な iPad では PC 高画質に近い絵を目指す。
    3. 互換（WebGL 2）：WebGPU が使えない環境、WebGPU で不具合が出る環境向け。
    4. VR（WebGL 2 ＋ WebXR）：Quest 3 単体向け。下の「VR 版」の節に従う。
    どの段階でも絵の方向性は変えず、密度だけを変える。
  - 重要な方針：基本の見た目（形、質感、光、色）は、WebGL 2 でも成り立つように作る。
    WebGPU でしか出せないものは、上乗せの演出に限る。
    こうすることで、クラウド環境で確認できる WebGL 2 の絵が、そのまま全段階の土台になる。
- 最新の iPad・iPhone を活かす：
  - 私の iPad・iPhone は最新の機種と最新の OS である。古い機種への対応は優先しない。
  - iOS・iPadOS の Safari の WebGPU には不具合の報告もある。表示の乱れや停止が出た場合は自動で互換に切り替わるようにし、
    設定画面で描画方式を「自動／WebGPU／WebGL 2」から選べるようにする。
  - 画面の細かさと滑らかさを活かし、解像度と fps の最適な組み合わせを、実機診断の結果から決める。
  - 新しい機種でもブラウザのタブが使えるメモリには上限がある。落ちないことを実機で確かめる。
  - タッチ操作は、確認用の簡易なものではなく、最後まで快適に遊べる正式な操作として作る。
    iPad では、無線のゲームパッドにも対応する。
- 予算表（Docs/WEB_BUDGET.md。最初の目標値。実機の結果で見直し、変更は理由とともに記録する）：
  - 最初のダウンロード（タイトル画面からステージ1を始められるまで）：圧縮後 25MB 以内
  - ステージごとの追加ダウンロード：圧縮後 30MB 以内。ステージは必要になってから読み込む
  - 全体：圧縮後 250MB 以内（画面版）。VR 版は別に集計する
  - 読み込み時間：光回線の PC で、URL を開いてからタイトル画面まで10秒以内
  - フレームレート：PC 高画質は常時60fps。モバイル高画質は60fps。互換は30fps以上。
    VR は常時72fps以上（可能なら90fps）
  - 品質段階ごとに、描画回数、ポリゴン数、テクスチャの総量の上限を決める
  - ビルドのたびに、容量の内訳（プログラム、テクスチャ、メッシュ、音、フォント）を記録し、増えた原因を説明する
- 容量を抑えながら見た目を保つ工夫：
  - テクスチャは原則 1K、主役級のみ 2K。近寄ったときの細かさは、シェーダーで作る模様や、細部用テクスチャの重ね掛けで補う。
  - 土の粒や組織の模様のように規則性のあるものは、画像に頼らずシェーダーで生成する。
  - メッシュは圧縮し、LOD を付ける。同じ形は使い回し（インスタンス化）、色や形の変化はシェーダーで作る。
  - 日本語の文字は、画面版では HTML と CSS で表示する（くっきり表示でき、容量も小さい）。
    フォントは、ゲームで使う文字だけを含めたものを同梱する。
- ブラウザ特有の決まり：
  - 音はユーザーが操作するまで鳴らせない。タイトル画面に「クリックして開始」を置き、そこで音を開始する。
  - マウスで視点を動かすにはポインターの固定が必要で、Esc で解除される。解除されたら自動で一時停止する。
  - 全画面表示のボタンを用意する。テレビでは全画面で遊ぶ前提にする。
  - セーブはブラウザの中に保存される。別のブラウザや端末には引き継がれないことを、設定画面に明記する。
    端末をまたいで続きから遊べるよう、進み具合を短い文字列として書き出し・読み込みできる機能を用意する。
  - タブを切り替えて戻ったとき、画面サイズや向きを変えたときに、表示や音が壊れないようにする。
  - シェーダーの初回コンパイルによる引っかかりを避けるため、読み込み中にあらかじめ準備しておく。
  - 実行に必要なファイルはすべてサイトに同梱する。外部のサイトから実行時に読み込むものを作らない。
- 読み込み画面：
  - 独自のデザインにする。進み具合を表示し、待ち時間に、登場する生き物の豆知識を1つずつ見せる。
- Netlify への公開：
  - 第1部で作ったサイトに公開し続ける。
  - 作業中の版は下書き用の URL で確かめ、節目の版だけを本番の URL に公開する。
  - 公開のたびに、URL を装飾なしの単独行で示す。
  - Netlify のプランの上限に近づいたら、その時点で私に知らせる。

## VR 版（Meta Quest 3）
土の中に自分が入り込む体験は、VR で最も力を発揮する。細菌の群れに囲まれ、頭上を根が走り、
ミミズが目の前を通り過ぎる。この「大きさの実感」を VR 版の最大の価値とする。

- 仕組み：
  - Quest 3 の標準ブラウザで URL を開き、「VR で遊ぶ」を押すと VR に入る。アプリのインストールは不要。
  - Three.js の WebXR 対応を使う。画面版と同じコードから作り、
    VR 用に変えるのは、カメラ、操作、UI、描画の密度だけにする。
  - コントローラーの3Dモデルなど、VR に必要な素材もサイトに同梱する。
- 性能（VR では滑らかさが最優先。コマ落ちは酔いに直結する）：
  - Quest 3 単体で常時72fps以上。可能なら90fps。
  - 左右の目の分を描くため、描画の負荷は画面版の約2倍になる。VR 専用の軽い密度を最初から設計する。
    - 半透明の重ね描きを減らす（水の膜、霧、粒子は VR では負荷が高い。数と面積を抑え、見せ場に集中させる）。
    - 光はあらかじめ焼き込んだものを中心にし、その場で計算する光と影は最小限にする。
    - 後処理は基本的に使わない。輪郭の滑らかさは MSAA で確保する。
    - 視線の周辺の解像度を下げる機能（フォビエーション）を使う。
  - 表示の乱れ、遅れ、片目だけのずれがないかを、実機で必ず確かめてもらう。
- 酔いにくさ（最重要）：
  - 座って遊ぶ形を標準にする。
  - 視界の一部に動かない枠（スーツのバイザーの縁）を置き、体の基準にする。
  - 移動の方法を複数用意し、設定で選べるようにする。
    なめらかな移動（速度は控えめ、加速と減速は穏やか）、短い距離を一瞬で進む移動、向きは一定の角度ずつ変える方式。
  - 移動中は視野の周辺を暗くする機能を入れる（強さを調整でき、切ることもできる）。
  - カメラを勝手に動かさない、揺らさない。演出でもプレイヤーの頭の動きを奪わない。
    地上の変化の演出は、プレイヤーをその場に立たせたまま、周りの世界が変わっていく形で見せる。
  - 水の膜の中を泳ぐ場面は特に酔いやすい。進む向きは頭か手の向きに合わせ、回転を伴う動きを避ける。
- 操作（Quest 3 のコントローラー）：
  - 左スティックで移動、右スティックで向きの変更、トリガーで道具、グリップでつかむ・張り付く。
  - スキャンは手首の端末を見る動作、道具は手に持って向ける動作にする。VR ならではの手触りを作る。
  - 生き物に手を近づけて観察できるようにする。
- UI と紹介カード：
  - UI は顔に貼り付けず、世界の中に置く。読みやすい距離（1.5〜2メートル相当）と大きさにする。
  - VR の中では HTML の文字は使えない。文字はパネルの画像として描き、くっきり読める解像度にする。
  - 初登場の紹介カードは、生き物の横に浮かぶパネルとして出す。字幕は視線の少し下に、ゆるやかについてくる形で出す。
  - 図鑑では、生き物の3Dモデルを手に取って回し、実物大と拡大を切り替えて見比べられるようにする。
- 地上の変化の演出：
  - 小さな体のまま地表に立ち、目の前で芽が伸び、頭上で花が開く様子を見せる。
    巨大な草花を見上げる体験を、VR 版の見せ場にする。
- 音：音の方向と距離が分かる立体的な音にする。頭上の雨、背後を通る生き物、足元の水の音を、位置で感じられるようにする。
- ヘッドセットなしでの確認：
  - VR の操作と UI を、普通の画面上で模擬できる確認モードを用意する。
  - WebXR のエミュレーターを使い、VR に入る・見回す・操作する流れを自動で確かめる。
  - Quest 3 の実機での確認は、各マイルストーンの最後に私に頼む。
    その前に、同じ内容を iPad・iPhone の Safari（画面版）で私が確認できる状態にしておく。
- 追加の案（余力があれば、調べて提案する。実装は私の指示を待つ）：
  - Quest 3 を PC につないで PC のブラウザから VR に入り、PC の GPU の性能で高画質の VR を描く方法。
  - 現実の部屋の映像に生き物を重ねて、図鑑の生き物を自分の部屋に置いて観察する機能。

土の中の小さな生き物たちと力を合わせて土を生き返らせ、地上に草を茂らせ、花を咲かせ、
最後には一本の大樹を満開にする。

  芽が出る、葉が広がる、つぼみが開く様子を、早回しで見せる。

## 実在の生き物だけを使う（最重要）
このゲームに登場する生き物は、微生物・小さな動物・虫・草・花・木のすべてを、
地球上に実在する種に基づかせる。架空の生き物は1つも出さない。主人公とその装備だけがフィクションである。

- 舞台を1つの実在の環境に定め、そこに実際にいる種でそろえる。
  指定がなければ「日本の里山（関東地方の雑木林と草地）」とする。
  同じ場所・同じ季節に実際に出会える組み合わせにし、病気と宿主、共生の相手どうしも、実在する組み合わせにする。
- 種の決め方：
  - 動物・植物・キノコは、種（和名と学名）まで決める。
  - 細菌やウイルスのように種まで絞る意味が薄いものは、属や実在する型まで決める。
  - 下に挙げる名前は候補の例である。採用する前に、信頼できる資料（大学・研究機関・博物館・図鑑・論文）で
    実在、分布、大きさ、姿、働きを確かめ、合わなければ実在する別の種に差し替える。
- 生き物台帳 Docs/SPECIES.md に、登場するすべての種を記録する。項目は次のとおり。
  和名、学名、分類、実際の大きさ、姿と色の特徴、動き方、土の中での働き、登場ステージ、
  初登場時の説明文、参考にした資料の出所。
  台帳にない生き物をゲームに登場させない。
- 姿の調べ方（この環境では参考写真を自分で見られない可能性が高い）：
  - まず、参考写真を自分で取得して見られるかを確かめる。見られるなら、種ごとに3点以上を見てから作る。
  - 見られない場合は、信頼できる資料の文章による記述から、姿を数値と言葉で書き出す。
    体長、体の比率、体節の数、脚の本数と付き方、触角、毛、殻、口の形、色、透け具合、動き方。
    これを「形の仕様書」として Docs/REFERENCE/species/ に種ごとに保存し、その仕様どおりに作る。
  - そのうえで、作ったモデルの画像を進捗確認ページに並べ、私に実物の写真と見比べるよう頼む。
    私が参考写真を添付した場合は、それを最優先の資料として使う。
  - 写真を見ずに作ったものを「写真と比べて確認した」と報告しない。確認の方法を正直に書く。
- 事実確認：台帳の内容は、制作に関わっていないサブエージェントに資料と突き合わせて確認させる。
  確かめられなかった記述は載せない。分からないことを推測で埋めない。
- 実在しない器官・能力・行動を足さない。目や表情を描き足す、擬人化する、といった脚色をしない。
  養分の流れなどを光で示す表示は、スーツのスキャン画面の表示として扱い、生き物そのものの性質に見せない。

候補の例（採用前に必ず確認する）：
- 細菌：根粒菌（Rhizobium 属）、硝化菌（Nitrosomonas 属、Nitrobacter 属）、枯草菌（Bacillus subtilis）、
  リンを溶かす細菌（Pseudomonas 属など）、放線菌（Streptomyces 属。土の匂いのもと。病原菌を抑える）
- 菌類：アーバスキュラー菌根菌（Rhizophagus irregularis など）、トリコデルマ（Trichoderma 属）、
  線虫捕食菌（Arthrobotrys 属など）、落ち葉を分解するキノコ、光るキノコ（ヤコウタケなど）
- 原生動物：土にすむ繊毛虫（Colpoda 属など）、アメーバ
- 線虫：細菌を食べる線虫（Caenorhabditis elegans など）、害虫に寄生する有益な線虫（Steinernema 属）
- 小さな動物：トビムシ（Folsomia candida など）、ササラダニの仲間、捕食性のダニ、クマムシ（オニクマムシなど）
- ミミズ：フトミミズの仲間
- バクテリオファージ（細菌に感染するウイルス。尾を持つ型など、実在する型）
- 向き合う相手：フザリウム（Fusarium oxysporum）、サツマイモネコブセンチュウ（Meloidogyne incognita）、
  コガネムシ類の幼虫（ドウガネブイブイなど）、ネキリムシ（カブラヤガの幼虫など）
- 植物：シロツメクサ（Trifolium repens）、レンゲソウ、スミレ、カントウタンポポ、
  大樹としてヤマザクラ、雑木林の木としてコナラ

## 初登場時の紹介と図鑑
生き物・植物が初めて登場したとき、それが何であるかを短く紹介する。

- 紹介の出し方：
  - 画面版では、その生き物にカメラがゆっくり寄り、動きがよく見える数秒間を作る。操作は止めすぎない。
    VR 版ではカメラを動かさず、生き物の横に紹介パネルを浮かべ、生き物を淡く照らして目を引く。
  - 紹介カードの内容は次のとおり。
    和名、学名、実際の大きさ（髪の毛の太さや米粒など、身近なものとの比較を添える）、
    何者で、土の中で何をしているかを、1〜2文で。
  - 同じ内容を、落ち着いたナレーションで読み上げる。字幕も出す。
  - 表示は5〜8秒。ボタンで早送りでき、もう一度見ることもできる。
  - 緊迫した場面の最中には出さず、落ち着いた瞬間まで待ってから出す。
  - 文字は、50インチのテレビから離れて座っても、iPad・iPhone の画面でも、VR の中でも読める大きさにする。
- 生き物以外でも、土を理解するうえで大事な要素（団粒、腐植、水の膜、根毛、根粒など）は、同じ形で紹介する。
- 図鑑：一度紹介した生き物は、図鑑に登録される。図鑑はいつでも開ける。
  - 3Dモデルを回して細部まで見られる。
  - 実際の大きさを、主人公や身近なものと並べて比べられる。
  - 姿の特徴、動き方、土の中での働き、仲間や相手との関係を、短い文章で読める。
  - 出会っていない生き物は、輪郭だけを表示する。
- 説明文はすべて生き物台帳の確認済みの内容から書く。事実と違うことを書かない。
  専門用語には、ひと言の言い換えを添える。
- 設定で、初登場の紹介を「すべて表示／名前だけ／表示しない」から選べるようにする。

## 根幹の考え方：「倒す」のではなく「育てる・つなぐ」
- 土の中の生き物は、基本的に仲間である。
  植物は光合成で作った糖を根から土に分け与え、微生物はその糖をもらう代わりに、
  窒素・リン・水などを植物に届ける。この「糖と養分の交換」をゲームの経済の中心に置く。
- すべての土と生き物に「土の活力（0〜1）」を持たせ、この1つの値で見た目・動き・音・進行を同時に動かす。
  - 見た目：乾いて固く灰色の土 → 湿り気があり、団粒がほぐれ、菌糸と根と生き物で満ちた黒い土
  - 音：風と砂の乾いた音 → 水のしずく、生き物の気配、澄んだ和音
  - 進行：区画の活力が一定を超えると根が伸びてきて、新しい道が開く
- プレイヤーが手を入れた場所は、その場で目に見えて生き返ること。これがこのゲーム最大の快感である。
- 病原菌や害虫と向き合う場面もあるが、主な手段は「味方を増やして土の調和を取り戻す」こと。
  多様な生き物がいる土では病気が広がりにくい、という実際の仕組みを遊びにする。
  どうしても必要な場面だけ、味方と協力して直接退ける。
- 生き物どうしの関係（食べる・食べられる、共生、抑え合う）は、実際の関係どおりに描く。

## 遊びの流れ
探索（土の粒のすき間を歩く、水の膜を泳ぐ、菌糸の上を滑る、ミミズのトンネルを進む）
→ 出会い（新しい生き物に出会い、紹介を見て、図鑑に登録される）
→ 観察（スキャンで、足りない養分・水・生き物と、その原因を見つける）
→ 手入れ（養分を運ぶ、生き物を呼ぶ、菌糸と根をつなぐ）
→ 山場（その区画の難所。干ばつ、病原菌の広がり、大きな害虫など）
→ 土の目覚めの演出
→ 地上の変化（発芽・成長・開花）
→ 断面図の更新と能力の強化

## 主人公の操作と道具
- 移動：土の粒のすき間を歩く・登る。水の膜の中は全方向に泳ぐ。菌糸の上を高速で滑走する。
  ミミズが掘ったトンネルを通る。場面によってはミミズやトビムシに乗る。
- スキャン：土の活力と、養分（窒素・リン・炭素）と水の流れを可視化する。
- 糖のしずく：根からもらった糖を置いて、微生物を呼び集め、増やす。
- 菌糸スプール：菌根菌の菌糸を導いて、根と根、区画と区画をつなぐ。
- 水のカプセル：乾いた場所に水を運び、水の膜を広げる。
- 合図のシグナル：化学的な合図を出して、拮抗菌や捕食性の生き物など、味方を呼び寄せる。
- エネルギーは糖。根の先端が補給地点とセーブ地点を兼ねる。
- 操作感は最重要。加減速、慣性、カメラの追従、当たり判定、手応えの一瞬の間、振動まで作り込む。
- 入力は、キーボード＋マウス、ゲームパッド、タッチ、Quest 3 のコントローラーの4通りに対応する。
  どの入力でも、最後まで快適に遊べること。
  菌糸の高速滑走やミミズに乗る場面は、VR 版では酔いにくい見せ方（速度を抑える、視野を絞る、乗り物の枠を見せる）に変える。

## 土の中の住人の役割
具体的な種は「実在の生き物だけを使う」の方針で決め、生き物台帳に記録する。
- 仲間：
  - 細菌：空気中の窒素を取り込む根粒菌、硝化菌、リンを溶かす細菌、病原菌を抑える放線菌
  - 菌類：根とつながり養分と水を運ぶ菌根菌、落ち葉を分解するキノコ、病原菌を抑えるトリコデルマ、
    線虫を捕らえる線虫捕食菌
  - 小さな動物：原生動物、有益な線虫、トビムシ、ササラダニ、クマムシ、捕食性のダニ
  - 大きな存在：土を耕しトンネルと団粒を作るミミズ、植物の根と根毛
  - バクテリオファージ（病原細菌を抑える味方として登場）
- 向き合う相手と障害：
  - 根腐れを起こす病原菌、病原細菌
  - 害虫：ネコブセンチュウ、コガネムシ類の幼虫、ネキリムシ
  - 環境：乾燥、水のたまりすぎによる酸欠、踏み固められた土、塩類のたまり、養分の偏り
- 大きさは実物どおりの比率を守る。
  細菌は約1〜2マイクロメートル、菌糸の太さは数マイクロメートル、原生動物は数十マイクロメートル、
  線虫は約1ミリ、トビムシは1〜2ミリ、ミミズは数センチ以上。
  スケールの驚きを演出に使う。ステージごとに主人公の縮小倍率を変えてよい
  （細菌と並ぶ大きさから、トビムシと並ぶ大きさまで）。倍率を変えるときは、画面で分かるように示す。

## ステージ構成（一粒の種から始まり、大樹の満開で終わる）
1. 種の目覚め：一粒の種のまわりの土。水の膜を広げ、眠っている細菌を起こす。
   固有の遊び＝水を運んで道を作る。　地上の変化＝発芽して双葉が開く。
2. 根のまわり：根毛の森。根が出す糖を微生物に届け、リンや窒素と交換する。
   固有の遊び＝糖と養分の交換の流れを作る。　地上の変化＝草が茂る。
3. 根粒の工場：シロツメクサの根にできるこぶ。根粒菌を迎え入れ、空気中の窒素を取り込む仕組みを立ち上げる。
   固有の遊び＝工場の立ち上げと稼働。　地上の変化＝シロツメクサの花畑が広がる。
4. 菌糸の網：菌根菌の菌糸が作る地下のネットワーク。離れた根どうしをつなぎ、養分と水を運ぶ。
   固有の遊び＝ネットワークの接続と輸送。　地上の変化＝若木が育つ。
5. 落ち葉の層：落ち葉が土に変わる場所。キノコ、トビムシ、ダニ、ミミズと協力して落ち葉を腐植に変える。
   固有の遊び＝分解のリレーと、ミミズに乗ってのトンネル掘り。　地上の変化＝春の草花が一面に咲く。
6. 病んだ土：病原菌とネコブセンチュウが広がり、花が枯れかけている区画。
   トリコデルマ、放線菌、線虫捕食菌、バクテリオファージ、捕食性のダニ、有益な線虫を呼び、土の調和を取り戻す。
   山場はコガネムシ類の幼虫（この大きさでは巨大な存在）。
   固有の遊び＝味方の布陣。　地上の変化＝枯れかけた花がよみがえる。
7. 大樹の根元：干ばつのあとの雨。これまでの仲間すべてを連携させ、大樹の根に養分と水を届ける。
   固有の遊び＝全ステージの仕組みの総動員。　地上の変化＝大樹（ヤマザクラを候補とする）が満開になり、土地全体が花で埋まる。
拡張候補：水辺の土、畑、砂地、苔の世界、朽ち木の中。
各ステージは、その場所の生き物の働きに由来する固有の遊びを必ず1つ持つこと。同じ遊びの色違いにしない。
各ステージで、新しく出会う生き物を3〜6種用意し、図鑑が少しずつ埋まっていく楽しさを作る。

## 映像の基準（最重要）
目標は「ブラウザで動いているとは信じられない」品質。
土の顕微鏡写真や自然ドキュメンタリーを見慣れた大人が、本物らしいと感じる絵を、
Web の予算の中で、50インチの大画面でも、iPad の高精細な画面でも、VR の中でも、粗が見えない水準で実現する。
- 描画の土台：Three.js の WebGPURenderer。物理ベースのマテリアル、HDR、トーンマッピング、
  後処理（ブルーム、被写界深度、色調整、周辺減光、わずかな粒状感）。
- 生き物と植物の再現（実物どおりに描く）：
  - 「実在の生き物だけを使う」の調べ方に従い、形の仕様書を作ってから作る。
  - 体のつくりを実物に合わせる。体節の数、脚の本数と付き方、触角、毛、殻、口の形、体の比率、透け具合。
    例：トビムシは脚が6本で腹に跳ねるための器官がある。ダニとクマムシは脚が8本。線虫に体節はない。
    ミミズには体節と環帯がある。花は花びら・おしべ・めしべの数と形、葉は葉脈と付き方を合わせる。
  - 色は、光学顕微鏡や肉眼で見える実際の色を基準にする。
    電子顕微鏡写真は白黒で、色付きのものは後から着色されているので、その色を使わない。
    微生物の多くは無色透明に近い。派手な色を付けない。
  - 動き方も実物に合わせる。線虫のくねり、トビムシの跳躍、ミミズの伸び縮み、繊毛虫の泳ぎ、
    菌糸の先端の伸び方、花の開き方。
  - VR では生き物を間近で、あらゆる角度から見られる。裏側や細部まで破綻のないモデルにする。
- 質感づくり：
  - 透け感：厚みの情報を焼き込み、光が透ける表現と、縁が光る表現を作る。
  - 濡れ：表面の水の膜を、二層の反射（クリアコート）で表す。
  - 屈折：水の膜や半透明の体を通して、向こう側がゆがんで見える表現を入れる。
  - 空気感：霧、浮遊する微粒子、光の筋を、軽い方法で重ねる。
  - 光：影を落とすライトは主人公のライトなど1〜2個に絞り、ほかは影なしのライトと、Blender で焼き込んだ光で補う。
  - 周囲の映り込みに使う環境の画像は、外部の素材に頼らず、自分で生成する。
  - 負荷の高い表現（屈折、被写界深度、多層の半透明）は、品質段階ごとに使う・使わないを決め、
    VR では軽い代わりの表現を用意する。
- 土の粒：石英の半透明の粒、粘土の薄片、黒い腐植、それらが固まった団粒。粒ごとに質感を変え、
  表面には水の膜が張り、光を屈折・反射させる。
- 水：粒と粒のあいだに張る水の膜と、その縁の曲面。水中は屈折とゆらぎ、浮遊する微粒子。
- 生きている感覚：菌糸は伸び、根は成長し、水は染み込み、生き物は常に動いている。静止した世界を作らない。
  動きは、頂点シェーダーでのアニメーションなど、軽く動く方法で作る。
- 群れ：糖に集まり増えていく細菌の群れ。PC 高画質とモバイル高画質では GPU 上の計算で数万、
  互換と VR ではインスタンス描画で数千を描く。
- ライティング：地下は本来まっ暗である。光源は、主人公のライト、地表近くに差し込むわずかな光、
  スキャン表示の光、実在する光るキノコに絞る。洞窟探検のような、暗部を恐れない映画的な露出にする。
- 地上の映像：植物の発芽・成長・開花を、実写の早回し映像のように、その場で描画して見せる。
  葉脈の透け、花びらの薄さ、朝露、木漏れ日、風の揺れまで作る。ここは明るく、色彩豊かに。
  地下の暗さとの対比が、このゲームの見せ場である。成長の順序と形の変化も、その種の実際の育ち方に合わせる。
  成長の動きは、Blender で段階ごとの形を作り、実行時になめらかにつなぐ方式にする。
- モデルの作り方（すべて bpy の Python スクリプトで作る）：
  - 種や部品ごとに1つのスクリプトにし、実行すれば同じモデルを何度でも作り直せるようにする。
  - ジオメトリノードや手続き的な形づくりで高解像度の形を作り、ローポリへ法線・AO・厚みを焼き込み、
    LOD を付けて GLB で書き出し、glTF Transform で最適化する。
  - この環境の CPU は少ない。焼き込みの解像度とサンプル数は、所要時間を測りながら現実的な値に決める。
  - 1つの元データから、品質段階ごとの軽さのモデルを自動で書き出せるようにする。
  - 作ったモデルは、Blender で4方向から描画した確認用の画像を必ず作り、自分の目で見て、形の仕様書と照らす。
- 主人公と、すべての生き物を、モデル、リグ、アニメーションまで含めて作る。
  主人公のスーツは硬質な素材にして、有機的な背景との対比を作る。VR 版では、自分の手と腕、バイザーの縁が見える。
- 大画面と高精細画面への対応：
  - PC 高画質では、内部の描画解像度と表示解像度の最適な組み合わせを、実機診断の結果から決める。
  - 輪郭のギザギザや、濡れた面のちらつきを残さない。
  - カメラの動きはなめらかにし、急な揺れや細かい振動を避ける。
  - 文字と UI は、テレビから離れて座っても読める大きさにする。
- 完成品に残してはいけないもの：基本図形のままの仮モデル、単色マテリアル、均一な照明、
  ゲーム的すぎる原色のエフェクト、実物と違う姿の生き物。
- 表現の強さ：虫やミミズの描写は「標準／控えめ」を設定で切り替えられるようにする。
  控えめでも、姿を実物と違うものに変えない（寄りの映像を減らす、距離を取る、といった方法にする）。
  VR では刺激が強いので、VR 版の初回に、この設定を選ぶ画面を出す。

## 音の基準
- 常に土の中にいると感じる音：頭上から響くくぐもった雨音や風、水のしずく、根がきしむ音、
  生き物が動く小さな音。
- 音楽は場面に応じて変化させる。探索・手入れ・山場・目覚めの層を重ね、土の活力に連動させる。
  ステージごとに音色の主題を変える
  （種＝ピアノの単音、根のまわり＝弦のピチカート、根粒＝温かい木管、菌糸の網＝ハープとアルペジオ、
  　落ち葉の層＝木の打楽器、病んだ土＝低い不協和から解決へ、大樹＝オーケストラと合唱）。
- 土が目覚める瞬間と、花が開く瞬間は、音楽が大きく開く。映像の変化と同時に鳴らす。
  地下の静けさから地上の豊かな響きへ移る落差を作る。
- 地上の場面では、鳥の声、風、葉ずれ、虫の羽音など、季節に合った自然音を重ねる。
- 新しい生き物の紹介には、短く上品な専用の音を付ける。図鑑に登録された瞬間が小さなごほうびになるようにする。
- 効果音は素材感のあるものにする（土の粒、水、菌糸、殻、粘り）。
- 作り方と鳴らし方：
  - 実行時は Web Audio API を直接使う。音量の滑らかな入れ替え、水の膜の中で高音を削るフィルター、
    空間の響き、音の方向と距離の表現を、ブラウザの機能で行う。
  - 音素材は、この環境で Python により合成して作り、ffmpeg で圧縮する。
    水、土、風、泡、電気的な音などは、合成で作りやすい。丁寧に作り込む。
  - 外部の音素材サイトには届かない前提とする。使う場合は、商用利用が可能で出所が明確なものだけにし、
    Docs/LICENSES.md に出所とライセンスを記録する。
  - 音楽は、まずコードで作曲して合成した仮の音源を入れ、場面との連動の仕組みを完成させる。
    合成では品質が足りない曲と、鳥や虫の声のように合成が難しい音については、
    必要な仕様（尺、テンポ、楽器、雰囲気、ほしい音の種類）を私に示す。私が素材を用意するかを判断する。
  - ナレーションは、台本を完成させ、仮の音声としてブラウザの読み上げ機能を使う。
    読み上げ機能が使えない機器では字幕だけにする。録音した音声に差し替えられる作りにしておく。
  - iPad・iPhone でも確実に再生できる形式にする。
- 聴く環境ごとに仕上げる。音の出力を「テレビ／ヘッドホン／VR」から選べるようにし、
  小さな音量でも台詞と大事な音が聞き取れるようにする。

## 技術方針
- 「採用する道具」の組み合わせで作る。使うライブラリの版を固定し、Docs/TECH.md に記録する。
- 構成：
  - 1つのコードから、画面版と VR 版を作る。カメラ・操作・UI の表示方法だけを差し替えられる作りにする。
  - タイトルとハブを含む最小の本体を最初に読み込み、ステージは後から読み込む。
  - 土の活力システム、養分の流れ、紹介カードと図鑑、セーブ、入力、音、UI は共通基盤にする。
  - 調整値はデータファイルに出し、コードに数値を埋め込まない。
  - 生き物のデータ（名前、学名、大きさ、説明文、モデル、音）は、種ごとに1つのデータにまとめ、
    生き物台帳と中身を一致させる。紹介カードと図鑑は、このデータから自動で作る。
- 画面版の UI は HTML と CSS で作り、スーツのバイザー表示として世界になじませる。
  画面の大きさ、縦横比、向きが変わっても崩れないようにする。
- 自動テストを用意する。ゲームの仕組み（活力、養分、進行、セーブ）は単体テスト、
  画面は Playwright による自動操作とスクリーンショットで確かめる。
- すべての変更を小さくコミットし、プッシュする。

## 進め方
全ステージを浅く作らない。ステージ1「種の目覚め」を最終品質まで仕上げ、基準が固まってから次へ進む。
どの段階でも、Netlify に公開した URL で動くものを常に保つ。
各マイルストーンは、画面版を先に仕上げ、同じ内容を VR 版でも動かしてから完了とする。
私の確認は、まず iPad・iPhone の Safari（画面版）、次に PC とテレビ、最後に Quest 3、の順で行う。
- M0 基盤：第1部の公開経路（画面版・VR 版・実機診断）、品質段階の切り替え、
  bpy による素材づくりの経路、ビルドと公開のスクリプト、独自の読み込み画面、
  土の活力システムの試作、舞台の地域の決定、ステージ1に登場する種の台帳と形の仕様書、予算表。
- M1 見た目の確立：種のまわりの土の一区画（歩いて30秒ほどの広さ）だけを最終品質で作り、Netlify に公開する。
  乾いて痩せた状態から、湿って生き物に満ちた状態へ変わる様子と、地上で種が発芽する様子を見せる。
  この区画に登場する生き物を2種以上仕上げ、初登場の紹介カードも動かす。
  すべての品質段階で動かす。VR 版は、同じ区画の中に立って見回し、歩けるところまで作る。
  ここで私の確認を受ける。実機診断の結果と、見た目の感想を私から受け取り、予算表と基準を見直す。
- M2 操作の確立：歩く・泳ぐ・菌糸を滑る・スキャン・糖のしずくの手触りを、M1 の環境の中で仕上げる。
  4通りの入力すべてに対応する。VR 版は、酔いにくさの設定と、手を使った操作をここで仕上げる。
- M3 ステージ1完成：探索、出会い、観察、手入れ、山場、土の目覚め、地上の変化、音、図鑑まで通しで遊べる。
  画面版と VR 版の両方で。
- M4 ハブ（土地の断面図）、セーブと進み具合の書き出し・読み込み、設定画面、タイトル画面、
  画面版と VR 版の行き来、ステージの後読み込み。
- M5 以降：ステージを1つずつ追加する（私の指示を受けてから。第3部の「ステージ追加」を使う）。
各マイルストーンの完了条件は GDD に明記する。

## 検証と報告
この環境でできる確認と、実機でしかできない確認を、はっきり分ける。

- この環境で自分で行う確認：
  - 作るたびに、Blender の確認用の画像と、Playwright で撮ったゲーム画面のスクリーンショット（WebGL 2）を
    自分の目で見て、形の仕様書や狙いと比べ、足りない点を言葉にして直す。これを最低3回繰り返してから報告する。
  - 決まったカメラの経路と操作を自動で再生し、同じ場面を毎回同じ条件で撮って、直す前後を比べる。
  - コンソールのエラーをゼロにする（WebGL 2 と WebGPU の両方で）。
  - 読み込むファイルの容量とその内訳を計測し、予算表と比べる。
  - 動画は、時間を一定の刻みで進めながら1コマずつ撮り、ffmpeg でつなげて作る
    （この環境の描画は遅いので、そのまま録画しても滑らかにならない）。
  - 画像を読み込めない場合は、そのことを最初に報告する。見ていないものを見たと言わない。
- 実機でしかできない確認（私に頼む）：
  - WebGPU での実際の見た目、fps、メモリ、操作の手触り、音の聞こえ方、VR の快適さ。
  - 頼むときは、開く URL、使う機器、見てほしい点を3つ以内で具体的に書く。
    実機診断ページの結果を貼ってもらう。気になる画面はスクリーンショットを送ってもらう。
  - Quest 3 では特に、コマ落ち、表示の乱れ、酔いやすさ、文字の読みやすさ、操作のしやすさを尋ねる。
  - 私が送った診断結果とスクリーンショットは、最優先の事実として扱い、次の作業に反映する。
- 自分で確かめられていないことは、確かめられていないと明記する。
- 節目ごとに、スクリーンショット5枚以上と、30〜60秒のプレイ動画を作り、
  進捗確認ページ（/progress/）に、生き物のモデルの確認用画像とあわせて並べて公開する。
- 報告は日本語で短く書く：公開 URL（画面版・VR 版・進捗確認・実機診断）、できたこと、見てほしい点、
  新しく登場した生き物の一覧（和名・学名）、容量と予算の比較、
  自己評価（映像・生き物の正確さ・操作・音・読み込みの軽さを各10点満点、理由と確認方法付き）、
  私に頼む実機確認、次にやること。
- URL は必ず装飾なしの単独行で示す。
- うまくいかないことは、原因を調べ、別の方法を試してから報告する。
- 区切りごとにコミットしてプッシュし、Docs/HANDOFF.md を更新する
  （現状、決定事項、既知の問題、次の一手、公開 URL、Netlify のサイト ID、環境の準備手順）。

## ステージ追加（例：「ステージ2の根のまわりを作って」）
1. 調査
   その場所の実際の構造と、そこに実在する生き物の種類、大きさ、色、質感、動き、働きを調べ、
   Docs/REFERENCE/（場所の名前）.md にまとめる。
   新しく登場させる種を生き物台帳に追加し、形の仕様書を作り、サブエージェントに事実確認させる。
2. 設計（GDD に追記してから作る）
   - 痩せた状態と豊かな状態の、見た目の差（3点以上）
   - その場所の生き物の働きに由来する固有の遊び（1つ）。画面版と VR 版それぞれでの遊ばせ方
   - 道のり：入口 → 3つの区域 → 山場。区域ごとの見せ場

3. 制作
   ステージ1で確立した基準を下回らないこと。
   共通基盤を再利用し、そのステージに固有の部分だけを新しく作る。ステージは後から読み込む形にする。
   画面版を先に仕上げ、続けて VR 版を仕上げる。
4. 検証
   自動操作での通しプレイ、エラーゼロ、予算表の範囲内。
   新しい生き物すべてに、確認用の画像、紹介カード、図鑑の項目があること。
5. 報告
   公開 URL、スクリーンショット、動画、容量、自己評価、進捗確認ページの更新、私に頼む実機確認の内容。

## 実機の結果を伝えるとき（例：診断結果の貼り付け、スクリーンショットの添付、「iPadだとこう見える」）
- 貼られた診断結果を読み取り、機器ごとの表に整理して Docs/DEVICE_RESULTS.md に追記する。
- 予算表の目標と比べ、届いていない項目と、その原因の候補を挙げる。
- 添付されたスクリーンショットを見て、狙いとの違いを書き出す。
- 対処を行い、公開し、もう一度確かめてほしい点を具体的に伝える。

## VR で酔う・カクつくとき（例：「VRで酔う」「VRがカクカクする」）
- 私から、どの場面で、どんな動きのときに起きたかを聞き取る。足りなければ1回だけ質問する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影の数を数え、VR の上限と比べる。
- 描画の負荷を下げる（半透明を減らす、光と影を軽くする、LOD を早める、粒子を減らす、描画解像度を調整する）。
- 酔いやすい動き（回転、急な加速、勝手なカメラの動き、高速の移動）を洗い出し、
  速度の調整、視野を絞る機能の強化、移動方法の変更で対処する。
- 対処後の版を公開し、私に Quest 3 での再確認を頼む。見てほしい点を具体的に書く。

## VR で動かない・表示がおかしいとき（例：「VRに入れない」「VRで画面が乱れる」）
- 私から、表示されたメッセージ、起きた手順、画面の様子を聞き取る。
- WebXR のエミュレーターで同じ手順を再現できるか試す。
- 原因の候補を挙げ、可能性の高い順に対処を試す。試したことと結果を表で報告する。

## iPad や iPhone で動かない・落ちる・表示がおかしいとき（例：「iPadで落ちる」）
- 私から、機種、OS の版、起きた場面、表示されたメッセージ、診断ページの結果を聞き取る。
- WebGPU で起きている場合は、設定で WebGL 2 に切り替えて同じ症状が出るかを私に確かめてもらい、原因を切り分ける。
- 読み込む素材の量、テクスチャの大きさ、描画解像度、後処理を見直し、メモリの使用を減らす。
- 対策後の版を公開し、私に実機での再確認を頼む。

## 読み込みが遅い・容量が大きいとき（例：「読み込みが遅い」）
- 読み込むファイルの容量の内訳を計測する。
- 大きい順に原因を5つ挙げる（テクスチャ、メッシュ、音、フォント、プログラムなど）。
- 見た目を落とさない対策から順に適用する（圧縮形式の見直し、解像度の調整、後読み込みへの移動、不要なコードの除去）。
- Netlify の配信設定（圧縮とキャッシュ）が正しく効いているかを確かめる。
- 対策ごとに、前後の容量を表で報告する。

## 生き物が本物と違うとき（例：「トビムシが本物と違う」。写真の添付があればそれを使う）
1. 私が添付した写真があれば、それを最優先の資料にする。
   なければ、その種の姿についての記述を新たに調べ直し、形の仕様書を見直す。
2. 現在のモデルの確認用の画像と見比べ、
   違いを「体のつくり・比率・色・透け具合・表面の質感・動き方」の6項目で書き出す。
3. 違いが大きい順に、モデルを作るスクリプトを直す。直すたびに確認用の画像を作り直す。
4. 台帳の記述に誤りが見つかったら、台帳、紹介カード、図鑑もあわせて直す。
5. 直す前と直した後の比較画像を、進捗確認ページに載せる。

## 紹介や図鑑を直したいとき（例：「説明が長い」「説明が難しい」「紹介が邪魔」）
- 説明文を、1〜2文で、専門用語に言い換えを添えた形に書き直す。事実は台帳から外れないこと。
- 表示の長さ、出すタイミング、見せ方、文字の大きさを、画面版と VR 版それぞれで見直す。
- 全種の紹介文を一覧にして、直す前と直した後を表で報告する。

## 映像がゲームっぽいとき（例：「映像がゲームっぽい」。スクリーンショットの添付があればそれを使う）
1. 現在の画面を、決まった場面で撮る。私が添付した画面や参考写真があれば、それと並べる。
2. 違いを「形・色・質感・光・動き・空気感」の6項目で書き出す。
3. 差が大きい順に3項目を直す。直すたびに同じ場面を撮り直して比べる。
4. 直す前と直した後の比較画像と、容量と描画負荷への影響を報告に添える。

## 大画面で粗が見えるとき（例：「テレビで見るとギザギザする」「カクつく」）
- 私から、どの場面で何が気になるかと、診断ページの結果を聞き取る。
- 輪郭のギザギザ、濡れた面のちらつき、ぼやけたテクスチャ、文字の小ささへの対策を行う。
- 引っかかりの原因（読み込み、シェーダーの準備、粒子、影）を調べて対処する。
- 内部の描画解像度、アンチエイリアスの設定を見直す。
- 公開し、同じ場面をもう一度確かめてもらう。

## 操作が気持ちよくないとき（例：「泳ぐ操作が気持ちよくない」）
- 対象（歩く／泳ぐ／菌糸の滑走／道具など）と入力方法（キーボード＋マウス／ゲームパッド／タッチ／Quest 3 のコントローラー）
  について、入力から動き出しまでの遅れ、加速と減速の曲線、慣性、カメラの追従と揺れ、
  手応え（一瞬の間・振動・音・光）を見直す。
- 調整値はデータファイルに出し、変更前と変更後の値を表で報告する。
- 設定画面に、その場で調整できる一時的なつまみを用意し、私が実機で好みの値を探せるようにする。

## 芽吹きや開花をもっと感動的にしたいとき（例：「開花の演出を作り直して」）
- 土の活力が上がるにつれて、水が染みる、菌糸が伸びる、生き物が集まる、根が伸びる、の順番を1秒単位で設計する。
- 画面版では、カメラが土の中から地上へ抜け、芽・葉・つぼみ・花の順に、早回しで見せる。
  VR 版では、プレイヤーを地表に立たせたまま、周りで植物が育っていく様子を見せる。
  光は朝の斜めの光を基本にする。成長の順序と形は、その種の実際の育ち方に合わせる。
- 音は地下の静けさから始め、地上に出た瞬間に音楽と自然音が開く。花が開く瞬間に和音の頂点を合わせる。
- 演出の絵コンテ（文章でよい）を先に書いてから実装する。

## 音が薄いとき（例：「音が薄い」）
- いま鳴っている音を一覧にし、無音になっている動作や場面を洗い出す。
- 足りない音を追加する：移動、接触、道具、仲間と相手、環境、地上の自然音、紹介と図鑑、UI。
- 音量のバランス、水の中のこもり具合、距離による減衰、VR での音の方向感を調整する。
- 追加した音による容量の増加を報告する。

## 動きが重いとき（例：「動きが重い」。診断結果の貼り付けがあればそれを使う）
目標は、PC 高画質とモバイル高画質で60fps、互換で30fps以上、VR で72fps以上。
- 診断結果から、どの機器のどの場面が目標を下回っているかを特定する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影、後処理、粒子の数を数え、重い原因の候補を挙げる。
- 見た目を落とさない対策から順に適用する。
- 公開し、同じ場面の診断をもう一度お願いする。

## ライブラリを新しい版に上げたいとき（例：「Three.jsを最新にして」）
- 最新の正式版と、その変更点のうちこのゲームに効くもの（描画、性能、WebGPU、VR、不具合の修正）を調べて報告する。
- 作業用の枝で版を上げ、自動テストとスクリーンショットの比較を行い、下書き用の URL に公開する。
- 問題がなければ切り替え、問題があれば原因と選択肢を報告する。Docs/TECH.md の版の記録を更新する。

## 全体の完成度を上げたいとき（例：「厳しい目で採点して」）
制作に関わっていない厳しいレビュアーの立場のサブエージェントに、スクリーンショットと動画と公開 URL の情報を渡して採点させる。
- 最初の5分で感じる「安っぽさ」と「待たされ感」を10個挙げる。
- 市販のAA級タイトルや、評価の高い Web の 3D 作品・VR 作品と比べて足りない点を、
  映像・生き物の正確さ・操作・音・演出・UI・読み込みの軽さ・VR の快適さに分けて挙げる。
- 効果が大きく手間が小さい順に並べ、上位5個を直す。
- 直す前と直した後の比較を、進捗確認ページに載せる。
