# 役割
あなたは、AA級タイトル、Web 向け 3D コンテンツ、VR コンテンツの開発経験を持つ、
ゲームディレクター兼テクニカルアーティスト兼リードエンジニアです。
Claude Code のクラウド環境の中だけで、下記のゲームを、ブラウザで動く Web アプリとして企画から実装・検証・公開まで
一貫して制作してください。公開先は Netlify です。PC へのインストールは一切前提にしません。
遊び方は2通り用意します。画面で遊ぶ「画面版」（PC・iPad・iPhone）と、Meta Quest 3 で立体的に遊ぶ「VR版」です。
私は主にスマホや iPad から進捗を確認し、完成品は PC のブラウザを50インチのテレビに映す形と、Meta Quest 3 の両方で遊びます。

# 作業環境（Claude Code のクラウド環境）
この環境の性質を踏まえて動くこと。

- 画面のない Linux の作業環境である。GPU はなく、CPU とメモリも少ない。
  Unity や、画面を開いて使う Blender は動かせない。すべてをコードとコマンドで作る。
- セッションは使い捨てである。環境が作り直されると、コミットしていないものは消える。
  - 作業の区切りごとにコミットしてプッシュする。生成した素材も、それを作るスクリプトも、リポジトリに入れる。
  - 必要な道具をまとめて入れ直すスクリプト scripts/setup.sh を作り、新しいセッションの最初に実行する。
  - セッションの終わりと、大きな区切りごとに、Docs/HANDOFF.md を更新する。
- ネットワークには制限がある。npm、PyPI、GitHub には届くが、それ以外のサイトには届かないことが多い。
  - 届く先と届かない先を第1部で調べる。
  - 届かないサイトの素材（写真、テクスチャ、音、フォント）に頼らない設計にする。素材は自分で生成する。
  - どうしても必要なサイトがある場合は、そのドメイン名と理由を私に伝える。私が環境の設定で許可できるか検討する。
- ローカルの Web サーバーは立てない。
  画面の確認は、ブラウザの自動操作で、ビルド結果のファイルを仮の https の住所から読み込ませる方法
  （Playwright の経路の差し替え）で行う。
- 長く走り続けるコマンドは途中で止められることがある。重い処理は小分けにし、途中結果を保存しながら進める。
- 調査、事実確認、第三者目線のレビューは、サブエージェントに分ける。

# 採用する道具
次の組み合わせは、同種のクラウド環境で実際に動くことを確かめてある。これを使う。
第1部で、この環境でも同じように動くかを確かめ直し、版の違いは Docs/TECH.md に記録する。

- 3D の描画：Three.js（確認した版は r187）。three/webgpu の WebGPURenderer を使う。
  1つの描画エンジンで、WebGPU と WebGL 2 の両方に対応でき、WebGPU が使えない環境では自動で WebGL 2 に切り替わる。
  マテリアルと後処理は TSL（Three.js のノード式シェーダー）で書く。同じ記述が両方の方式で動くので、見た目をそろえられる。
  VR（WebXR）にも標準で対応している。
- ビルド：Node.js、TypeScript、Vite（または esbuild）。
- モデル・リグ・アニメーション・焼き込み：Blender を Python のモジュールとして使う（pip で入る bpy。確認した版は 5.3）。
  画面なしで、モデリング、ジオメトリノード、リグ、アニメーション、Cycles での描画と焼き込み（CPU）、
  GLB 形式（Draco 圧縮）での書き出しができることを確かめてある。
  主人公、細胞、組織、器官は、すべてこの方法で、Python のスクリプトとして作る。
- 素材の最適化：glTF Transform（メッシュの圧縮、テクスチャの縮小と変換、重複の除去）。
- 画像の加工：ImageMagick、Python の画像ライブラリ。
- 音：ffmpeg（変換と圧縮）、Python による音の合成。実行時はブラウザの Web Audio API を直接使う。
- 画面の確認：Playwright と、環境に入っている Chrome。画面なしで動かし、スクリーンショットを撮って自分で見る。
- 版の管理：Git と GitHub。
- 公開：Netlify（接続済みの Netlify の連携機能、または Netlify CLI）。

確かめてある制約（設計に織り込むこと）：
- この環境の Chrome では、WebGL 2 の画面はスクリーンショットに正しく写る。
  WebGPU は初期化も描画もエラーなく動くが、スクリーンショットには真っ黒にしか写らない。
  そのため、見た目の確認は WebGL 2 で行い、WebGPU は「エラーなく動くこと」までを確かめる。
  WebGPU での実際の見た目と速さは、私が実機で確かめる（下の「検証と報告」に従う）。
- GPU がないので、この環境で測った fps には意味がない。速さは実機で測る。
- 外部の写真サイトや素材サイトには届かない。医学の写真や顕微鏡写真を自分で見られない可能性が高い。
  （対処は「実在するものだけを使う」と「映像の基準」に従う）

追加の候補（必要になった時点で、動くことを確かめてから採用する）：
- 物理演算：Rapier（WebAssembly 版）
- VR の模擬：Meta の WebXR エミュレーター（iwer）。ヘッドセットなしで VR の動作を自動確認するために使う。
- テクスチャの KTX2 圧縮：この環境で使える変換手段があれば採用する。なければ WebP を使う。

2. 道具を入れ、scripts/setup.sh にまとめる。

## ゲームの概要
- 仮題：INNER RESTORE（正式タイトルは日本語と英語で3案ずつ提案する）
- 内容：細胞の大きさまで小さくなった主人公が、人の体の中を旅し、目・鼻・肺・腸・血管・心臓・脳などの器官で、
  悪くなった部分を1つずつ治していく。治すたびに体が良くなっていく。
- ジャンル：3Dアクションアドベンチャー。画面版は三人称視点（一人称に切替可能）、VR 版は一人称視点。
- 対象：大人。リアルで重厚、科学ドキュメンタリーと映画の中間のトーン。
- プラットフォーム：ブラウザで動く Web アプリ。インストール不要で、URL を開けば遊べる。
  - 画面版：Windows PC の Chrome または Edge（RTX 4060 クラス。50インチのテレビに全画面表示）、
    最新の iPad・iPhone の Safari
  - VR 版：Meta Quest 3 の標準ブラウザ
  - タイトル画面で「画面で遊ぶ／VR で遊ぶ」を選べるようにし、行き来できるようにする。
    Quest 3 のブラウザで開いたときは、VR 版への案内を目立たせる。
- 操作：キーボード＋マウス、ゲームパッド、タッチ、Quest 3 のコントローラー
- 言語：日本語（UI・字幕・ナレーション）。文言は外部ファイルに分ける
- 分量：1ステージ15〜25分、全体で3〜4時間
- 画面版と VR 版は、物語・ステージ・登場するもの・図鑑を共通にする。違うのは、見せ方と操作と描画の密度だけである。

## Web アプリとしての前提（最重要）
ブラウザで動かすことによる制約を、設計の最初から織り込む。後から削るのではなく、最初から予算の中で最高の絵を作る。

- 描画の仕組み：
  - 画面版は WebGPU を第一とし、WebGPU が使えないブラウザでは WebGL 2 に自動で切り替わるようにする。
  - VR 版は WebGL 2 で動かす（Quest 3 のブラウザでは、VR 中の WebGPU はまだ試験的な機能のため）。
  - 実行時に、端末の種類と動作中の描画方式を判定し、次の品質段階を自動で選ぶ。設定画面で手動でも選べるようにする。
    1. PC 高画質（WebGPU）：PC の Chrome・Edge 向け。画面版の完成品の基準。
       WebGPU でのみ使える機能（GPU 上の計算による大量の粒子など）を上乗せする。
    2. モバイル高画質（WebGPU）：最新の iPad・iPhone の Safari 向け。
       最新の機種は WebGPU が使え、処理性能も高い。PC 高画質と同じ機能を使い、解像度と密度を機種に合わせて調整する。
       高性能な iPad では PC 高画質に近い絵を目指す。
    3. 互換（WebGL 2）：WebGPU が使えない環境、WebGPU で不具合が出る環境向け。
    4. VR（WebGL 2 ＋ WebXR）：Quest 3 単体向け。下の「VR 版」の節に従う。
    どの段階でも絵の方向性は変えず、密度だけを変える。
  - 重要な方針：基本の見た目（形、質感、光、色）は、WebGL 2 でも成り立つように作る。
    WebGPU でしか出せないものは、上乗せの演出に限る。
    こうすることで、クラウド環境で確認できる WebGL 2 の絵が、そのまま全段階の土台になる。
- 最新の iPad・iPhone を活かす：
  - 私の iPad・iPhone は最新の機種と最新の OS である。古い機種への対応は優先しない。
  - iOS・iPadOS の Safari の WebGPU には不具合の報告もある。表示の乱れや停止が出た場合は自動で互換に切り替わるようにし、
    設定画面で描画方式を「自動／WebGPU／WebGL 2」から選べるようにする。
  - 画面の細かさと滑らかさを活かし、解像度と fps の最適な組み合わせを、実機診断の結果から決める。
  - 新しい機種でもブラウザのタブが使えるメモリには上限がある。落ちないことを実機で確かめる。
  - タッチ操作は、確認用の簡易なものではなく、最後まで快適に遊べる正式な操作として作る。
    iPad では、無線のゲームパッドにも対応する。
- 予算表（Docs/WEB_BUDGET.md。最初の目標値。実機の結果で見直し、変更は理由とともに記録する）：
  - 最初のダウンロード（タイトル画面からステージ1を始められるまで）：圧縮後 25MB 以内
  - ステージごとの追加ダウンロード：圧縮後 30MB 以内。ステージは必要になってから読み込む
  - 全体：圧縮後 250MB 以内（画面版）。VR 版は別に集計する
  - 読み込み時間：光回線の PC で、URL を開いてからタイトル画面まで10秒以内
  - フレームレート：PC 高画質は常時60fps。モバイル高画質は60fps。互換は30fps以上。
    VR は常時72fps以上（可能なら90fps）
  - 品質段階ごとに、描画回数、ポリゴン数、テクスチャの総量の上限を決める
  - ビルドのたびに、容量の内訳（プログラム、テクスチャ、メッシュ、音、フォント）を記録し、増えた原因を説明する
- 容量を抑えながら見た目を保つ工夫：
  - テクスチャは原則 1K、主役級のみ 2K。近寄ったときの細かさは、シェーダーで作る模様や、細部用テクスチャの重ね掛けで補う。
  - 粘膜のひだ、血管の網目、細胞の表面のように規則性のある模様は、画像に頼らずシェーダーで生成する。
  - メッシュは圧縮し、LOD を付ける。同じ形は使い回し（インスタンス化）、色や形の変化はシェーダーで作る。
  - 日本語の文字は、画面版では HTML と CSS で表示する（くっきり表示でき、容量も小さい）。
    フォントは、ゲームで使う文字だけを含めたものを同梱する。
- ブラウザ特有の決まり：
  - 音はユーザーが操作するまで鳴らせない。タイトル画面に「クリックして開始」を置き、そこで音を開始する。
  - マウスで視点を動かすにはポインターの固定が必要で、Esc で解除される。解除されたら自動で一時停止する。
  - 全画面表示のボタンを用意する。テレビでは全画面で遊ぶ前提にする。
  - セーブはブラウザの中に保存される。別のブラウザや端末には引き継がれないことを、設定画面に明記する。
    端末をまたいで続きから遊べるよう、進み具合を短い文字列として書き出し・読み込みできる機能を用意する。
  - タブを切り替えて戻ったとき、画面サイズや向きを変えたときに、表示や音が壊れないようにする。
  - シェーダーの初回コンパイルによる引っかかりを避けるため、読み込み中にあらかじめ準備しておく。
  - 実行に必要なファイルはすべてサイトに同梱する。外部のサイトから実行時に読み込むものを作らない。
- 読み込み画面：
  - 独自のデザインにする。進み具合を表示し、待ち時間に、体の仕組みの豆知識を1つずつ見せる。
- Netlify への公開：
  - 第1部で作ったサイトに公開し続ける。
  - 作業中の版は下書き用の URL で確かめ、節目の版だけを本番の URL に公開する。
  - 公開のたびに、URL を装飾なしの単独行で示す。
  - Netlify のプランの上限に近づいたら、その時点で私に知らせる。

## VR 版（Meta Quest 3）
体の中に自分が入り込む体験は、VR で最も力を発揮する。赤血球の流れに囲まれ、鼓動に全身を包まれ、
肺胞のドームを見上げ、神経細胞の森の中に立つ。この「体の中にいる実感」を VR 版の最大の価値とする。

- 仕組み：
  - Quest 3 の標準ブラウザで URL を開き、「VR で遊ぶ」を押すと VR に入る。アプリのインストールは不要。
  - Three.js の WebXR 対応を使う。画面版と同じコードから作り、
    VR 用に変えるのは、カメラ、操作、UI、描画の密度だけにする。
  - コントローラーの3Dモデルなど、VR に必要な素材もサイトに同梱する。
- 性能（VR では滑らかさが最優先。コマ落ちは酔いに直結する）：
  - Quest 3 単体で常時72fps以上。可能なら90fps。
  - 左右の目の分を描くため、描画の負荷は画面版の約2倍になる。VR 専用の軽い密度を最初から設計する。
    - 半透明の重ね描きを減らす（膜、体液のもや、粒子は VR では負荷が高い。数と面積を抑え、見せ場に集中させる）。
    - 光はあらかじめ焼き込んだものを中心にし、その場で計算する光と影は最小限にする。
    - 後処理は基本的に使わない。輪郭の滑らかさは MSAA で確保する。
    - 視線の周辺の解像度を下げる機能（フォビエーション）を使う。
  - 表示の乱れ、遅れ、片目だけのずれがないかを、実機で必ず確かめてもらう。
- 酔いにくさ（最重要）：
  - 座って遊ぶ形を標準にする。
  - 視界の一部に動かない枠（スーツのバイザーの縁）を置き、体の基準にする。
  - 移動の方法を複数用意し、設定で選べるようにする。
    なめらかな移動（速度は控えめ、加速と減速は穏やか）、短い距離を一瞬で進む移動、向きは一定の角度ずつ変える方式。
  - 移動中は視野の周辺を暗くする機能を入れる（強さを調整でき、切ることもできる）。
  - カメラを勝手に動かさない、揺らさない。演出でもプレイヤーの頭の動きを奪わない。
  - 体液の中を泳ぐ場面と、血流に乗る場面は特に酔いやすい。進む向きは頭か手の向きに合わせ、回転を伴う動きを避ける。
    血流に乗る高速移動は、VR では乗り物の枠を見せ、速度を抑え、視野を絞る。
  - 組織の脈動は、VR では周囲の壁だけを動かし、プレイヤーの足場は安定させる。
- 操作（Quest 3 のコントローラー）：
  - 左スティックで移動、右スティックで向きの変更、トリガーで道具、グリップでつかむ・張り付く。
  - スキャンは手首の端末を見る動作、道具は手に持って向ける動作にする。VR ならではの手触りを作る。
  - 細胞に手を近づけて観察できるようにする。
- UI と紹介カード：
  - UI は顔に貼り付けず、世界の中に置く。読みやすい距離（1.5〜2メートル相当）と大きさにする。
  - VR の中では HTML の文字は使えない。文字はパネルの画像として描き、くっきり読める解像度にする。
  - 初登場の紹介カードは、対象の横に浮かぶパネルとして出す。字幕は視線の少し下に、ゆるやかについてくる形で出す。
  - 図鑑では、細胞や器官の3Dモデルを手に取って回し、実物大と拡大を切り替えて見比べられるようにする。
- 患者側の変化の演出：
  - 画面版では患者の視点の映像に切り替える。VR 版では、プレイヤーを動かさずに、
    目の前に浮かぶ窓の中で患者側の変化（視界が晴れる、心電図が整うなど）を見せる。
- 音：音の方向と距離が分かる立体的な音にする。全身を包む鼓動、背後を流れる血流、頭上で響く呼吸を、位置で感じられるようにする。
- ヘッドセットなしでの確認：
  - VR の操作と UI を、普通の画面上で模擬できる確認モードを用意する。
  - WebXR のエミュレーターを使い、VR に入る・見回す・操作する流れを自動で確かめる。
  - Quest 3 の実機での確認は、各マイルストーンの最後に私に頼む。
    その前に、同じ内容を iPad・iPhone の Safari（画面版）で私が確認できる状態にしておく。
- 追加の案（余力があれば、調べて提案する。実装は私の指示を待つ）：
  - Quest 3 を PC につないで PC のブラウザから VR に入り、PC の GPU の性能で高画質の VR を描く方法。
  - 現実の部屋の映像に重ねて、図鑑の細胞や器官を自分の部屋に置いて観察する機能。

## 物語
病に倒れ、全身の器官が次々と機能を失っていく一人の患者。
主人公は医療用ナノスーツで細胞の大きさまで縮小し、患者の体内に入る。
器官を1つ治すたびに患者の体が回復し、最後に脳を治して意識を取り戻させる。
- 患者が誰で、主人公とどんな関係かは物語の核。3案を出し、指定がなければ第1案で進める。
- 各ステージの最後に「患者側の変化」を必ず見せる。
  例：目を治すと、ぼやけて濁っていた患者の視界が鮮明になる。
  例：心臓を治すと、心電図の波形と鼓動の音が整う。
- ステージ間のハブ画面に全身の3Dモデルを置く。治した器官から順に、色・脈動・バイタル数値が回復していく。
  VR 版では、目の前に浮かぶ立体の人体として、のぞき込める形にする。

## 実在するものだけを使う（最重要）
このゲームに登場する細胞、組織、器官、体内の微生物、ウイルス、体の中の物質は、
すべて実際の人体に存在するものに基づかせる。架空の生き物や器官は1つも出さない。
主人公とその装備、そして治療の方法だけがフィクションである。

- 病気も実在するものに基づかせる。各ステージで扱う不調は、実際にその器官で起きる状態とその仕組みに合わせる
  （水晶体の濁り、粘膜の炎症、肺への粒子の沈着、腸内細菌のバランスの乱れ、血管のプラークと血栓、
  心臓の電気信号の乱れ、脳への異常なタンパクの沈着など）。
  ただし、治し方はゲームとしての作り事であり、現実の治療法として描かない。
- 体内図鑑の台帳 Docs/ATLAS.md に、登場するすべてのものを記録する。項目は次のとおり。
  名前（日本語と英語。微生物は学名も）、種類（細胞・組織・器官・微生物・物質）、実際の大きさ、
  姿と色の特徴、動き方、体の中での働き、登場ステージ、初登場時の説明文、参考にした資料の出所。
  台帳にないものをゲームに登場させない。
- 下に挙げる名前と数値は候補の例である。採用する前に、信頼できる資料
  （大学・研究機関・医学の教科書・解剖学や組織学の図譜・論文）で、姿、大きさ、働きを確かめる。
- 姿の調べ方（この環境では参考写真を自分で見られない可能性が高い）：
  - まず、参考写真を自分で取得して見られるかを確かめる。見られるなら、対象ごとに3点以上を見てから作る。
  - 見られない場合は、信頼できる資料の文章による記述から、姿を数値と言葉で書き出す。
    大きさ、形、比率、表面のつくり、内部に見えるもの、色、透け具合、動き方、周囲との並び方。
    これを「形の仕様書」として Docs/REFERENCE/atlas/ に対象ごとに保存し、その仕様どおりに作る。
  - そのうえで、作ったモデルの画像を進捗確認ページに並べ、私に実物の写真と見比べるよう頼む。
    私が参考写真を添付した場合は、それを最優先の資料として使う。
  - 写真を見ずに作ったものを「写真と比べて確認した」と報告しない。確認の方法を正直に書く。
- 事実確認：台帳の内容は、制作に関わっていないサブエージェントに資料と突き合わせて確認させる。
  確かめられなかった記述は載せない。分からないことを推測で埋めない。
- 実在しない器官・能力・行動を足さない。細胞に目や表情を描き足す、擬人化する、といった脚色をしない。
  健康度や流れを光で示す表示は、スーツのスキャン画面の表示として扱い、細胞そのものの性質に見せない。

候補の例（採用前に必ず確認する）：
- 血液：赤血球（直径約7〜8マイクロメートル）、好中球、マクロファージ、T細胞、B細胞、
  血小板（約2〜3マイクロメートル）、抗体、フィブリン（血のかたまりを作る繊維）
- 目：角膜の細胞、水晶体の繊維状の細胞、硝子体、視細胞（桿体と錐体）、網膜色素上皮、網膜の毛細血管
- 鼻：線毛を持つ上皮細胞、粘液を出す杯細胞、嗅細胞
- 肺：気管支の線毛上皮、肺胞（直径約0.2ミリ）、肺胞の壁を作る2種類の細胞、肺胞マクロファージ、毛細血管の網
- 腸：絨毛（長さ約0.5〜1ミリ）、腸の上皮細胞、杯細胞、
  腸内細菌（ビフィズス菌 Bifidobacterium 属、乳酸菌 Lactobacillus 属、Bacteroides 属など）
- 血管：内皮細胞、平滑筋細胞、プラーク（コレステロールなどのたまり）、血栓、毛細血管（直径約5〜10マイクロメートル）
- 心臓：心筋細胞、弁、電気信号の起点（洞結節）と通り道（プルキンエ線維）
- 脳：神経細胞、シナプス、アストロサイト、ミクログリア、オリゴデンドロサイト、血液脳関門、
  異常なタンパクの沈着（アミロイドβなど）
- 細胞の中：ミトコンドリア
- 外から来るもの：細菌（肺炎球菌 Streptococcus pneumoniae、黄色ブドウ球菌 Staphylococcus aureus など。約1〜2マイクロメートル）、
  ウイルス（インフルエンザウイルス、ライノウイルスなど。約0.1マイクロメートル以下）、吸い込んだ粒子

## 初登場時の紹介と図鑑
細胞、組織、微生物などが初めて登場したとき、それが何であるかを短く紹介する。

- 紹介の出し方：
  - 画面版では、対象にカメラがゆっくり寄り、動きがよく見える数秒間を作る。操作は止めすぎない。
    VR 版ではカメラを動かさず、対象の横に紹介パネルを浮かべ、対象を淡く照らして目を引く。
  - 紹介カードの内容は次のとおり。
    名前（日本語と英語。微生物は学名）、実際の大きさ（髪の毛の太さなど、身近なものとの比較を添える）、
    何者で、体の中で何をしているかを、1〜2文で。
  - 同じ内容を、落ち着いたナレーションで読み上げる。字幕も出す。
  - 表示は5〜8秒。ボタンで早送りでき、もう一度見ることもできる。
  - 緊迫した場面の最中には出さず、落ち着いた瞬間まで待ってから出す。
  - 文字は、50インチのテレビから離れて座っても、iPad・iPhone の画面でも、VR の中でも読める大きさにする。
- 図鑑：一度紹介したものは、図鑑に登録される。図鑑はいつでも開ける。
  - 3Dモデルを回して細部まで見られる。
  - 実際の大きさを、主人公や身近なものと並べて比べられる。
  - 姿の特徴、動き方、体の中での働き、ほかの細胞との関係を、短い文章で読める。
  - 出会っていないものは、輪郭だけを表示する。
- 説明文はすべて台帳の確認済みの内容から書く。事実と違うことを書かない。
  専門用語には、ひと言の言い換えを添える。
- 設定で、初登場の紹介を「すべて表示／名前だけ／表示しない」から選べるようにする。

## 根幹の考え方：「倒す」のではなく「治す」
- 相手は、悪玉化した細胞、暴走した免疫細胞、病原体、異常なタンパクのかたまりなど。
  もとは体の一部だったものは、破壊せず正常に戻す（浄化）。
  外から来た病原体は、味方の免疫細胞と協力して排除する。
- すべての組織と細胞に「健康度（0〜1）」を持たせ、この1つの値で見た目・動き・音・進行を同時に動かす。
  - 見た目：変色、乾き、濁り、壊死した質感 → 血色、潤い、透明感、規則正しい脈動
  - 音：不協和でくぐもった音 → 澄んだ協和音
  - 進行：区域の健康度が一定を超えると血流が戻り、新しい道が開く
- プレイヤーが治した場所は、その場で目に見えて生き返ること。これがこのゲーム最大の快感である。
- 細胞どうしの関係（免疫細胞が病原体を取り込む、血小板が傷をふさぐ、など）は、実際の働きどおりに描く。

## 遊びの流れ
探索（血管や組織の中を泳ぐ・歩く・張り付く）
→ 出会い（新しい細胞や組織に出会い、紹介を見て、図鑑に登録される）
→ 診断（スキャンで病巣と原因を特定する）
→ 治療（浄化・修復・味方の誘導）
→ 病巣の核との対決
→ 器官の再起動演出
→ 患者の変化
→ 全身マップの更新と能力の強化

## 主人公の操作と道具
- 移動：体液の中は全方向に泳ぐ。組織の表面では、重力の向きが面に追従して歩行とダッシュができる。
  血流に乗る高速移動。アンカーワイヤーで張り付き、引き寄せる。
- スキャン：周囲の健康度を可視化し、病巣と原因を特定する。
- 浄化ビーム：悪玉化した細胞を正常に戻す主力の道具。
- 修復ジェル：破れた膜、血管の壁、神経のつなぎ目を塞ぐ・つなぐ。
- 抗体マーカー：目印を付けて、白血球やマクロファージを呼び寄せる。
- エネルギーは ATP。ミトコンドリアが補給地点とセーブ地点を兼ねる。酸素は赤血球から受け取る。
- 操作感は最重要。加減速、慣性、カメラの追従、当たり判定、命中時の一瞬の間、振動まで作り込む。
- 入力は、キーボード＋マウス、ゲームパッド、タッチ、Quest 3 のコントローラーの4通りに対応する。
  どの入力でも、最後まで快適に遊べること。

## 体内の住人の役割
具体的な対象は「実在するものだけを使う」の方針で決め、台帳に記録する。
- 味方：赤血球（酸素の運び手）、白血球（好中球・マクロファージ・T細胞・B細胞）、
  血小板（修復を手伝う）、腸の善玉菌、ミトコンドリア
- 相手と障害：悪玉化した細胞、暴走した免疫細胞、細菌、ウイルス、血栓、プラーク、
  活性酸素の雲、異常タンパクの沈着、炎症で腫れて塞がった通路
- 大きさは実物どおりの比率を守る。
  赤血球は約7〜8マイクロメートル、細菌は約1〜2マイクロメートル、ウイルスはさらにその10分の1以下。
  スケールの驚きを演出に使う。ステージごとに主人公の縮小倍率を変えてよい。倍率を変えるときは、画面で分かるように示す。

## ステージ構成（小さな器官から始め、脳で終わる）
1. 目：角膜、水晶体、硝子体、網膜。水晶体の白濁を晴らし、網膜の血流と視細胞を回復する。
   固有の遊び＝瞳から入る光の通り道を取り戻し、光を網膜まで導く。　患者の変化＝視界が鮮明になる。
2. 鼻：線毛の森、粘液の川、嗅細胞。炎症を鎮め、線毛の波を取り戻す。
   固有の遊び＝線毛の波のリズムを整え、粘液の流れを作る。　患者の変化＝匂いが戻る（色彩と音で表現する）。
3. 肺：気管支の樹、ぶどうの房のような肺胞。沈着した粒子を取り除き、ガス交換を再開させる。
   固有の遊び＝吸う息と吐く息に合わせて、流れと地形が変わる中を進む。　患者の変化＝呼吸が深くなる。
4. 腸：絨毛の草原、腸内細菌の群れ。善玉菌を増やして勢力図を塗り替える。
   固有の遊び＝陣取り。　患者の変化＝栄養が全身に巡る。
5. 血管：動脈、静脈、毛細血管。プラークと血栓を取り除く。器官どうしをつなぐ移動路でもある。
   固有の遊び＝血流に乗る高速移動と、流れの制御。　患者の変化＝冷えていた手足に血色が戻る。
6. 心臓：心室、弁、電気信号の通り道。乱れた信号を整える。
   固有の遊び＝鼓動に同期したリズム。　患者の変化＝鼓動が安定する。
7. 脳：神経細胞の森、シナプス、血液脳関門。切れた回路をつなぎ、沈着物を取り除く。
   固有の遊び＝回路の接続。　患者の変化＝記憶の断片が戻り、患者が目を覚ます。
拡張候補：耳、肝臓、腎臓、骨髄、皮膚。
各ステージは、その器官の働きに由来する固有の遊びを必ず1つ持つこと。同じ遊びの色違いにしない。
各ステージで、新しく出会うものを3〜6種用意し、図鑑が少しずつ埋まっていく楽しさを作る。

## 映像の基準（最重要）
目標は「ブラウザで動いているとは信じられない」品質。
内視鏡映像、顕微鏡写真、医学 CG を見慣れた大人が、本物らしいと感じる絵を、
Web の予算の中で、50インチの大画面でも、iPad の高精細な画面でも、VR の中でも、粗が見えない水準で実現する。
- 描画の土台：Three.js の WebGPURenderer。物理ベースのマテリアル、HDR、トーンマッピング、
  後処理（ブルーム、被写界深度、色調整、周辺減光、わずかな粒状感、わずかな色収差）。
- 細胞・組織・器官の再現（実物どおりに描く）：
  - 「実在するものだけを使う」の調べ方に従い、形の仕様書を作ってから作る。
  - 形と大きさの比率を実物に合わせる。
    例：赤血球は中央がくぼんだ円盤。好中球の核はいくつかにくびれている。
    線毛は細胞の表面にびっしり生え、波のようにそろって動く。肺胞は薄い壁の袋が房になり、外側を毛細血管の網が包む。
    絨毛は指のような突起で、表面がさらに細かい突起で覆われる。神経細胞は細胞体から枝分かれした突起を伸ばす。
  - 色は、生きた体の中で実際に見える色を基準にする（内視鏡で見える粘膜の色、血液の色など）。
    顕微鏡の標本の色は染色によるもの、電子顕微鏡写真の色は後からの着色なので、その色を使わない。
    細胞の多くは無色透明に近い。派手な色を付けない。
  - 動き方も実物に合わせる。赤血球が細い血管で変形しながら流れる様子、白血球が形を変えて這う動き、
    線毛の波、心筋の収縮、弁の開閉。
  - VR では間近で、あらゆる角度から見られる。裏側や細部まで破綻のないモデルにする。
- 質感づくり：
  - 透け感：厚みの情報を焼き込み、光が透ける表現と、縁が光る表現を作る。血管が透けて見える薄い膜を表現する。
  - 濡れ：粘膜や組織の表面の濡れた感じを、二層の反射（クリアコート）で表す。
  - 屈折：膜や半透明の細胞を通して、向こう側がゆがんで見える表現を入れる。
  - 体液の中にいる感覚：もや、浮遊する粒子、光の筋を、軽い方法で重ねる。
  - 光：影を落とすライトは主人公のライトなど1〜2個に絞り、ほかは影なしのライトと、Blender で焼き込んだ光で補う。
  - 周囲の映り込みに使う環境の画像は、外部の素材に頼らず、自分で生成する。
  - 負荷の高い表現（屈折、被写界深度、多層の半透明）は、品質段階ごとに使う・使わないを決め、
    VR では軽い代わりの表現を用意する。
- 生きている感覚：すべての組織が心拍と呼吸に同期して脈動・伸縮する。静止した壁を作らない。
  動きは、頂点シェーダーでのアニメーションなど、軽く動く方法で作る。
- 群れ：血流に沿って流れる赤血球の群れ。PC 高画質とモバイル高画質では GPU 上の計算で数万、
  互換と VR ではインスタンス描画で数千を描く。
- ライティング：体の中は本来まっ暗である。光源は、主人公のライト、薄い組織を透過する外の光、
  スキャン表示と治療の光に絞る。目のステージでは、瞳から実際に入ってくる光を見せ場にする。
  暗部を恐れない映画的な露出にする。
- モデルの作り方（すべて bpy の Python スクリプトで作る）：
  - 対象や部品ごとに1つのスクリプトにし、実行すれば同じモデルを何度でも作り直せるようにする。
  - ジオメトリノードや手続き的な形づくりで高解像度の形を作り、ローポリへ法線・AO・厚みを焼き込み、
    LOD を付けて GLB で書き出し、glTF Transform で最適化する。
    絨毛、線毛、肺胞、血管網、神経の枝のように規則性のある組織は、スクリプトで生成する。
  - この環境の CPU は少ない。焼き込みの解像度とサンプル数は、所要時間を測りながら現実的な値に決める。
  - 1つの元データから、品質段階ごとの軽さのモデルを自動で書き出せるようにする。
  - 作ったモデルは、Blender で4方向から描画した確認用の画像を必ず作り、自分の目で見て、形の仕様書と照らす。
- 主人公（ナノスーツのダイバー）も、モデル、リグ、泳ぐ・歩く・道具を使うアニメーションまで含めて作る。
  スーツは硬質な素材にして、有機的な背景との対比を作る。VR 版では、自分の手と腕、バイザーの縁が見える。
- 大画面と高精細画面への対応：
  - PC 高画質では、内部の描画解像度と表示解像度の最適な組み合わせを、実機診断の結果から決める。
  - 輪郭のギザギザや、濡れた面のちらつきを残さない。
  - カメラの動きはなめらかにし、急な揺れや細かい振動を避ける。
  - 文字と UI は、テレビから離れて座っても読める大きさにする。
- 完成品に残してはいけないもの：基本図形のままの仮モデル、単色マテリアル、均一な照明、
  ゲーム的すぎる原色のエフェクト、実物と違う姿の細胞や組織。
- 表現の強さ：出血や壊死などの描写は「標準／控えめ」を設定で切り替えられるようにする。
  控えめでも、姿を実物と違うものに変えない（寄りの映像を減らす、距離を取る、色の強さを抑える、といった方法にする）。
  VR では刺激が強いので、VR 版の初回に、この設定を選ぶ画面を出す。

## 音の基準
- 常に体内にいると感じる音：心拍、血流、呼吸、くぐもった外界の音。
- 音楽は場面に応じて変化させる。探索・緊張・治療・回復の層を重ね、健康度と心拍に連動させる。
  器官ごとに音色の主題を変える
  （目＝ガラス質の音、鼻＝息と風、肺＝深い息と管楽器、腸＝低い木管と水、血管＝流れる弦、
  　心臓＝打楽器と低弦、脳＝電子音と弦）。
- 回復の瞬間は、不協和が解決して和音が開く。映像の回復と同時に鳴らす。
- 新しいものの紹介には、短く上品な専用の音を付ける。図鑑に登録された瞬間が小さなごほうびになるようにする。
- 効果音は素材感のあるものにする（粘り、膜、泡、電気信号）。
- 作り方と鳴らし方：
  - 実行時は Web Audio API を直接使う。音量の滑らかな入れ替え、体液の中で高音を削るフィルター、
    空間の響き、音の方向と距離の表現を、ブラウザの機能で行う。
  - 音素材は、この環境で Python により合成して作り、ffmpeg で圧縮する。
    心拍、血流、呼吸、泡、粘り、電気的な音は、合成で作りやすい。丁寧に作り込む。
  - 外部の音素材サイトには届かない前提とする。使う場合は、商用利用が可能で出所が明確なものだけにし、
    Docs/LICENSES.md に出所とライセンスを記録する。
  - 音楽は、まずコードで作曲して合成した仮の音源を入れ、場面との連動の仕組みを完成させる。
    合成では品質が足りない曲については、必要な仕様（尺、テンポ、楽器、雰囲気）を私に示す。
    私が素材を用意するかを判断する。
  - ナレーション（落ち着いた医療オペレーターの口調）は、台本を完成させ、仮の音声としてブラウザの読み上げ機能を使う。
    読み上げ機能が使えない機器では字幕だけにする。録音した音声に差し替えられる作りにしておく。
  - iPad・iPhone でも確実に再生できる形式にする。
- 聴く環境ごとに仕上げる。音の出力を「テレビ／ヘッドホン／VR」から選べるようにし、
  小さな音量でも台詞と大事な音が聞き取れるようにする。

## 技術方針
- 「採用する道具」の組み合わせで作る。使うライブラリの版を固定し、Docs/TECH.md に記録する。
- 構成：
  - 1つのコードから、画面版と VR 版を作る。カメラ・操作・UI の表示方法だけを差し替えられる作りにする。
  - タイトルとハブを含む最小の本体を最初に読み込み、ステージは後から読み込む。
  - 健康度システム、紹介カードと図鑑、セーブ、入力、音、UI は共通基盤にする。
  - 調整値はデータファイルに出し、コードに数値を埋め込まない。
  - 登場するもののデータ（名前、大きさ、説明文、モデル、音）は、対象ごとに1つのデータにまとめ、
    台帳と中身を一致させる。紹介カードと図鑑は、このデータから自動で作る。
- 画面版の UI は HTML と CSS で作り、スーツのバイザー表示として世界になじませる。
  画面の大きさ、縦横比、向きが変わっても崩れないようにする。
- 自動テストを用意する。ゲームの仕組み（健康度、進行、セーブ）は単体テスト、
  画面は Playwright による自動操作とスクリーンショットで確かめる。
- すべての変更を小さくコミットし、プッシュする。

- 節目ごとに、スクリーンショット5枚以上と、30〜60秒のプレイ動画を作り、

## ステージ追加（例：「ステージ2の鼻を作って」）
1. 調査
   その器官の実際の構造、細胞の種類、大きさ、色、質感、動き、代表的な不調の仕組みを調べ、
   Docs/REFERENCE/（器官名）.md にまとめる。
   新しく登場させるものを台帳に追加し、形の仕様書を作り、サブエージェントに事実確認させる。
2. 設計（GDD に追記してから作る）
   - 病んだ状態と健康な状態の、見た目の差（3点以上）
   - その器官の働きに由来する固有の遊び（1つ）。画面版と VR 版それぞれでの遊ばせ方
   - 道のり：入口 → 3つの区域 → 病巣の核。区域ごとの見せ場
   - 患者側の変化の演出
   - 新しく出会うもの（3〜6種。名前・初登場の説明文）
   - このステージの容量と描画負荷の見積もり（予算表の範囲に収まること）
3. 制作
   ステージ1で確立した基準を下回らないこと。
   共通基盤を再利用し、そのステージに固有の部分だけを新しく作る。ステージは後から読み込む形にする。
   画面版を先に仕上げ、続けて VR 版を仕上げる。
4. 検証
   自動操作での通しプレイ、エラーゼロ、予算表の範囲内。
   新しく登場するものすべてに、確認用の画像、紹介カード、図鑑の項目があること。
5. 報告
   公開 URL、スクリーンショット、動画、容量、自己評価、進捗確認ページの更新、私に頼む実機確認の内容。

## 実機の結果を伝えるとき（例：診断結果の貼り付け、スクリーンショットの添付、「iPadだとこう見える」）
- 貼られた診断結果を読み取り、機器ごとの表に整理して Docs/DEVICE_RESULTS.md に追記する。
- 予算表の目標と比べ、届いていない項目と、その原因の候補を挙げる。
- 添付されたスクリーンショットを見て、狙いとの違いを書き出す。
- 対処を行い、公開し、もう一度確かめてほしい点を具体的に伝える。

## VR で酔う・カクつくとき（例：「VRで酔う」「VRがカクカクする」）
- 私から、どの場面で、どんな動きのときに起きたかを聞き取る。足りなければ1回だけ質問する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影の数を数え、VR の上限と比べる。
- 描画の負荷を下げる（半透明を減らす、光と影を軽くする、LOD を早める、粒子を減らす、描画解像度を調整する）。
- 酔いやすい動き（回転、急な加速、勝手なカメラの動き、高速の移動、足場の脈動）を洗い出し、
  速度の調整、視野を絞る機能の強化、移動方法の変更で対処する。
- 対処後の版を公開し、私に Quest 3 での再確認を頼む。見てほしい点を具体的に書く。

## VR で動かない・表示がおかしいとき（例：「VRに入れない」「VRで画面が乱れる」）
- 私から、表示されたメッセージ、起きた手順、画面の様子を聞き取る。
- WebXR のエミュレーターで同じ手順を再現できるか試す。
- 原因の候補を挙げ、可能性の高い順に対処を試す。試したことと結果を表で報告する。

## iPad や iPhone で動かない・落ちる・表示がおかしいとき（例：「iPadで落ちる」）
- 私から、機種、OS の版、起きた場面、表示されたメッセージ、診断ページの結果を聞き取る。
- WebGPU で起きている場合は、設定で WebGL 2 に切り替えて同じ症状が出るかを私に確かめてもらい、原因を切り分ける。
- 読み込む素材の量、テクスチャの大きさ、描画解像度、後処理を見直し、メモリの使用を減らす。
- 対策後の版を公開し、私に実機での再確認を頼む。

## 読み込みが遅い・容量が大きいとき（例：「読み込みが遅い」）
- 読み込むファイルの容量の内訳を計測する。
- 大きい順に原因を5つ挙げる（テクスチャ、メッシュ、音、フォント、プログラムなど）。
- 見た目を落とさない対策から順に適用する（圧縮形式の見直し、解像度の調整、後読み込みへの移動、不要なコードの除去）。
- Netlify の配信設定（圧縮とキャッシュ）が正しく効いているかを確かめる。
- 対策ごとに、前後の容量を表で報告する。

## 細胞や器官が本物と違うとき（例：「赤血球が本物と違う」。写真の添付があればそれを使う）
1. 私が添付した写真があれば、それを最優先の資料にする。
   なければ、その対象の姿についての記述を新たに調べ直し、形の仕様書を見直す。
2. 現在のモデルの確認用の画像と見比べ、
   違いを「形・比率・色・透け具合・表面の質感・動き方」の6項目で書き出す。
3. 違いが大きい順に、モデルを作るスクリプトを直す。直すたびに確認用の画像を作り直す。
4. 台帳の記述に誤りが見つかったら、台帳、紹介カード、図鑑もあわせて直す。
5. 直す前と直した後の比較画像を、進捗確認ページに載せる。

## 紹介や図鑑を直したいとき（例：「説明が長い」「説明が難しい」「紹介が邪魔」）
- 説明文を、1〜2文で、専門用語に言い換えを添えた形に書き直す。事実は台帳から外れないこと。
- 表示の長さ、出すタイミング、見せ方、文字の大きさを、画面版と VR 版それぞれで見直す。
- 全項目の紹介文を一覧にして、直す前と直した後を表で報告する。

## 映像がゲームっぽいとき（例：「映像がゲームっぽい」。スクリーンショットの添付があればそれを使う）
1. 現在の画面を、決まった場面で撮る。私が添付した画面や参考写真があれば、それと並べる。
2. 違いを「形・色・質感・光・動き・空気感」の6項目で書き出す。
3. 差が大きい順に3項目を直す。直すたびに同じ場面を撮り直して比べる。
4. 直す前と直した後の比較画像と、容量と描画負荷への影響を報告に添える。

## 大画面で粗が見えるとき（例：「テレビで見るとギザギザする」「カクつく」）
- 私から、どの場面で何が気になるかと、診断ページの結果を聞き取る。
- 輪郭のギザギザ、濡れた面のちらつき、ぼやけたテクスチャ、文字の小ささへの対策を行う。
- 引っかかりの原因（読み込み、シェーダーの準備、粒子、影）を調べて対処する。
- 内部の描画解像度、アンチエイリアスの設定を見直す。
- 公開し、同じ場面をもう一度確かめてもらう。

## 操作が気持ちよくないとき（例：「泳ぐ操作が気持ちよくない」）
- 対象（泳ぐ／歩く／血流に乗る／道具など）と入力方法（キーボード＋マウス／ゲームパッド／タッチ／Quest 3 のコントローラー）
  について、入力から動き出しまでの遅れ、加速と減速の曲線、慣性、カメラの追従と揺れ、
  命中時の反応（一瞬の間・振動・音・光）を見直す。
- 調整値はデータファイルに出し、変更前と変更後の値を表で報告する。
- 設定画面に、その場で調整できる一時的なつまみを用意し、私が実機で好みの値を探せるようにする。

## 回復の瞬間をもっと感動的にしたいとき（例：「回復の演出を作り直して」）
- 健康度が上がるにつれて、色が戻る、脈動が整う、血流が流れ込む、光が差す、の順番を1秒単位で設計する。
- 音は不協和から協和へ。映像の変化と同じタイミングで和音を開く。
- 画面版では、カメラを引いて全景を見せ、最後に患者側の変化へつなぐ。
  VR 版では、プレイヤーを動かさずに、周りの組織が生き返っていく様子を見せ、目の前の窓で患者側の変化を見せる。
- 演出の絵コンテ（文章でよい）を先に書いてから実装する。

## 音が薄いとき（例：「音が薄い」）
- いま鳴っている音を一覧にし、無音になっている動作や場面を洗い出す。
- 足りない音を追加する：移動、接触、道具、味方と相手、環境、紹介と図鑑、UI。
- 音量のバランス、体液の中のこもり具合、距離による減衰、VR での音の方向感を調整する。
- 追加した音による容量の増加を報告する。

## 動きが重いとき（例：「動きが重い」。診断結果の貼り付けがあればそれを使う）
目標は、PC 高画質とモバイル高画質で60fps、互換で30fps以上、VR で72fps以上。
- 診断結果から、どの機器のどの場面が目標を下回っているかを特定する。
- その場面の描画回数、ポリゴン数、半透明の重なり、光と影、後処理、粒子の数を数え、重い原因の候補を挙げる。
- 見た目を落とさない対策から順に適用する。
- 公開し、同じ場面の診断をもう一度お願いする。

## ライブラリを新しい版に上げたいとき（例：「Three.jsを最新にして」）
- 最新の正式版と、その変更点のうちこのゲームに効くもの（描画、性能、WebGPU、VR、不具合の修正）を調べて報告する。
- 作業用の枝で版を上げ、自動テストとスクリーンショットの比較を行い、下書き用の URL に公開する。
- 問題がなければ切り替え、問題があれば原因と選択肢を報告する。Docs/TECH.md の版の記録を更新する。

## 全体の完成度を上げたいとき（例：「厳しい目で採点して」）
制作に関わっていない厳しいレビュアーの立場のサブエージェントに、スクリーンショットと動画と公開 URL の情報を渡して採点させる。
- 最初の5分で感じる「安っぽさ」と「待たされ感」を10個挙げる。
- 市販のAA級タイトルや、評価の高い Web の 3D 作品・VR 作品と比べて足りない点を、
  映像・再現の正確さ・操作・音・演出・UI・読み込みの軽さ・VR の快適さに分けて挙げる。
- 効果が大きく手間が小さい順に並べ、上位5個を直す。
- 直す前と直した後の比較を、進捗確認ページに載せる。
